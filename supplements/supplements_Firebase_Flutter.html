Firebase avec Flutter :

Introduction :

Ce syllabus constitue un parcours complet destiné à accompagner la conception et le développement d'une application Flutter multiplateforme sécurisée, reposant sur les services Firebase.

L'objectif est de construire progressivement une application capable de fonctionner sur Android, iOS et PC/Web, tout en utilisant une infrastructure Firebase commune pour l'authentification, la gestion des utilisateurs, le stockage des données et la sécurité.

La formation commence par la mise en place de l'environnement de développement et la configuration de Firebase. Elle évolue ensuite progressivement vers la création d'un système d'authentification complet et sécurisé.

Une attention particulière est consacrée à la sécurité des comptes utilisateurs. Le parcours comprend notamment :

  • la création d'un compte avec une adresse email et un mot de passe;

  • la vérification de l'adresse email;

  • la vérification du numéro de téléphone par SMS;

  • l'utilisation de l'authentification multifacteur (MFA);

  • l'intégration de Google Authenticator;

  • la gestion des sessions et des différents états d'un compte;

  • la protection des écrans et des fonctionnalités de l'application;

  • la gestion des données avec Cloud Firestore;

  • la mise en place de règles de sécurité Firebase;

  • la gestion des utilisateurs et des administrateurs;

  • la protection contre les accès non autorisés;

  • l'utilisation de Firebase App Check;

  • la mise en place de fonctions backend sécurisées.

Chaque module est conçu pour être suivi progressivement. Les concepts sont expliqués avant leur mise en pratique, puis accompagnés des éléments nécessaires à leur intégration dans le projet : architecture, organisation des fichiers, configuration et code source.

L'objectif final est d'obtenir une application dont la sécurité ne repose pas uniquement sur le code Flutter, mais sur une architecture complète combinant Flutter, Firebase Authentication, Cloud Firestore, Security Rules, App Check et backend sécurisé.

Ce syllabus doit ainsi servir à la fois de cours, de guide de développement et de référence technique, permettant de construire le projet étape par étape et de revenir facilement sur chaque partie lors de son évolution ou de sa maintenance.

Qu'est-ce que Firebase ?

Firebase est une plateforme de services backend permettant de fournir à une application différentes fonctionnalités sans devoir développer soi-même l'intégralité de l'infrastructure serveur.

Dans notre projet, Firebase pourra notamment fournir :

  • authentification;

  • base de données Firestore;

  • stockage de fichiers;

  • fonctions backend;

  • sécurité;

  • vérification d'applications;

Firebase permet de disposer d'une grande partie de cette infrastructure sous forme de services intégrables dans Flutter.

FlutterFire CLI est l'outil permettant de faciliter la configuration des applications Flutter avec Firebase.

Initialisation de Firebase :

Après avoir configuré Firebase, il faut initialiser Firebase au démarrage de l'application.

Le principe sera d'utiliser Firebase Core.

Le fichier main.dart évoluera progressivement.

Exemple :

import 'package:firebase_core/firebase_core.dart';
import 'package:flutter/material.dart';

import 'firebase_options.dart';

Future<void> main() async {
    WidgetsFlutterBinding.ensureInitialized();

    await Firebase.initializeApp(
        options: DefaultFirebaseOptions.currentPlatform,
    );

    runApp(const MyApp());
}

Cette étape est fondamentale.

Elle permet à l'application Flutter d'initialiser Firebase avant d'utiliser les services Firebase.

Pourquoi WidgetsFlutterBinding.ensureInitialized() ?

Avant d'exécuter certaines opérations Flutter asynchrones avant runApp(), il faut s'assurer que le binding est correctement initialisé.

C'est notamment nécessaire dans notre cas puisque nous allons initialiser Firebase avant de lancer l'application.

Le principe est :

Démarrage
   │
   ▼
Initialisation Flutter
   │
   ▼
Initialisation Firebase
   │
   ▼
runApp()
   │
   ▼
Application

Sécurité de la configuration Firebase :

Une confusion fréquente consiste à considérer les informations présentes dans la configuration Firebase comme des secrets.

Il faut distinguer :

Configuration Firebase
        ≠
Secret backend

Certaines informations utilisées pour les applications clientes sont destinées à être distribuées avec l'application.

La sécurité ne doit donc pas reposer sur le fait de cacher simplement la configuration Firebase.

La véritable protection reposera notamment sur :

  • Authentication;

  • Security Rules;

  • App Check;

  • contrôle des permissions;

  • backend sécurisé;

  • gestion correcte des secrets côté serveur.

Cette distinction sera essentielle dans les modules de sécurité.

Ce qui ne doit jamais être placé dans l'application cliente :

Les secrets réellement sensibles ne doivent pas être intégrés directement dans le code Flutter.

Par exemple :

  • clés privées;

  • secrets d'administration;

  • credentials de serveur;

  • clés privées de services backend;

  • tokens permanents privilégiés.

Ces éléments devront être conservés côté serveur ou dans des systèmes adaptés de gestion des secrets.

Authentification : définition :

L'authentification consiste à répondre à la question Qui est cette personne ?

Par exemple, lorsqu'un utilisateur saisit les informations suivantes, l'application doit pouvoir déterminer si ces informations permettent d'identifier correctement un compte.

Email :
alice@example.com

Mot de passe :
********

L'authentification permet donc de vérifier l'identité d'un utilisateur.

Authentification et autorisation :

Il est extrêmement important de ne pas confondre ces deux concepts.

Authentification :

L'authentification répond : Qui es-tu ?.

Exemple :

Utilisateur
   ↓
Connexion
   ↓
Firebase vérifie l'identité
   ↓
Utilisateur authentifié

Autorisation :

L'autorisation répond : Qu'as-tu le droit de faire ?.

Exemple :

Utilisateur authentifié
        │
        ├── Peut lire son profil
        │
        ├── Peut modifier son profil
        │
        └── Ne peut pas modifier le profil d'un autre utilisateur

Cette distinction deviendra essentielle lorsque nous étudierons Firestore Security Rules.

Pourquoi utiliser Firebase Authentication ?

Créer soi-même un système d'authentification sécurisé est une tâche complexe.

Il faut notamment gérer :

  • les mots de passe;

  • le stockage sécurisé des informations;

  • les sessions;

  • les tokens;

  • les renouvellements de tokens;

  • les réinitialisations de mots de passe;

  • la vérification email;

  • les connexions sociales;

  • les numéros de téléphone;

  • la MFA;

  • les protections contre les abus.

Firebase Authentication fournit une infrastructure permettant de gérer une grande partie de ces mécanismes.

Notre application pourra donc utiliser Firebase comme système d'identité.

  • téléphone;

        ↓

Cela permettra de construire progressivement un système d'authentification renforcé.

FirebaseAuth :

Le point d'accès principal au service Authentication est FirebaseAuth.instance.

On peut considérer cet objet comme le point d'entrée permettant à l'application de communiquer avec Firebase Authentication.

Exemple :

final auth = FirebaseAuth.instance;

Nous pourrons ensuite utiliser auth.currentUser pour récupérer l'utilisateur actuellement authentifié.

L'utilisateur courant :

Une notion essentielle de Firebase Authentication est celle de l'utilisateur actuellement connecté.

Firebase permet de savoir si un utilisateur est actuellement authentifié et, le cas échéant, d'accéder aux informations associées à son compte.

Pour cela, nous utiliserons :

FirebaseAuth.instance.currentUser

Cette propriété retourne l'utilisateur actuellement connecté.

Si aucun utilisateur n'est connecté, la valeur retournée sera null.

On peut donc représenter la situation ainsi :

FirebaseAuth
     │
     ▼
currentUser
     │
 ┌───┴────┐
 │        │
 ▼        ▼
User     null
 │        │
 │        └── Aucun utilisateur connecté
 │
 └── Utilisateur connecté

Un exemple simple serait :

final user =  FirebaseAuth.instance.currentUser;

if (user != null) {
    print('Utilisateur connecté');
} else {
    print('Aucun utilisateur connecté');
}

Cette vérification sera utilisée très fréquemment dans notre application.

Cependant, dans l'architecture finale, nous éviterons de répéter cette logique directement dans chaque écran.

Nous créerons progressivement une gestion centralisée de l'état d'authentification.

La classe User :

Lorsque Firebase Authentication identifie un utilisateur, Flutter peut accéder à un objet de type User.

Cet objet représente l'identité de l'utilisateur authentifié.

Il contient différentes informations utiles.

Par exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print(user.uid);
    print(user.email);
    print(user.displayName);
}

Nous utiliserons principalement ces informations pour identifier l'utilisateur et construire progressivement son profil dans Firestore.

Le UID utilisateur :

Chaque utilisateur Firebase possède un identifiant unique appelé UID.

UID signifie User ID.

Cet identifiant est particulièrement important dans notre architecture.

Utilisateur
     │
     ▼
Firebase Authentication
     │
     ▼
UID
     │
     ▼
Profil Firestore

Nous pourrons ensuite utiliser cet UID pour associer les données Firestore au bon utilisateur.

Par exemple, une structure de données pourra progressivement ressembler à :

users
│
├── uid_abc123
│      ├── email
│      ├── displayName
│      └── createdAt
│
├── uid_xyz456
│      ├── email
│      ├── displayName
│      └── createdAt
│
└── ...

L'UID est donc une pièce fondamentale de la relation entre Firebase Authentication et Cloud Firestore.

¨Pourquoi ne pas utiliser l'adresse email comme identifiant ?

Il serait possible de penser que l'adresse email pourrait servir à identifier directement un utilisateur.

Cependant, l'email n'est pas le meilleur identifiant pour notre architecture.

Un utilisateur peut notamment modifier certaines informations de son compte.

L'UID, quant à lui, est l'identifiant unique attribué au compte Firebase.

Nous utiliserons donc principalement :

UID
 │
 ├── Profil utilisateur
 ├── Données personnelles
 ├── Documents Firestore
 └── Autorisations

L'adresse email restera une information associée au compte, mais elle ne remplacera pas l'UID comme identifiant principal de nos données.

Informations principales de l'utilisateur :

L'objet User expose différentes propriétés.

Parmi les plus importantes pour notre projet, on retrouvera notamment :

  • uid : identifiant unique de l'utilisateur;

  • email : adresse email associée au compte;

  • emailVerified : indique si l'adresse email a été vérifiée;

  • displayName : nom affiché lorsqu'il est défini;

  • photoURL : URL éventuelle de la photo de profil;

  • phoneNumber : numéro de téléphone associé au compte lorsqu'il est défini.

On peut accéder à ces informations à partir de l'utilisateur courant :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print('UID : ${user.uid}');
    print('Email : ${user.email}');
    print('Email vérifié : ${user.emailVerified}');
    print('Nom : ${user.displayName}');
    print('Photo : ${user.photoURL}');
    print('Téléphone : ${user.phoneNumber}');
}

Certaines de ces propriétés peuvent être null.

Par exemple, un utilisateur nouvellement créé avec uniquement une adresse email et un mot de passe pourra ne pas avoir de displayName, de photoURL ou de phoneNumber.

Il faut donc toujours tenir compte de cette possibilité dans le code.

Dans notre projet, nous commencerons principalement avec une authentification utilisant une adresse email et un mot de passe.

Cependant, l'architecture doit rester suffisamment flexible pour accueillir d'autres méthodes d'authentification.

Vérifier si l'adresse email a été vérifiée :

La propriété emailVerified permet de savoir si l'utilisateur a confirmé son adresse email.

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    if (user.emailVerified) {
        print('Adresse email vérifiée');
    } else {
        print('Adresse email non vérifiée');
    }
}

Cette propriété retourne une valeur booléenne. Elle peut être donc true ou false.

Le parcours pourra être représenté ainsi :

Compte créé
    │
    ▼
Email non vérifié
    │
    ▼
Envoi du mail de vérification
    │
    ▼
Utilisateur clique sur le lien
    │
    ▼
Email vérifié

Cette étape sera particulièrement importante dans le parcours d'inscription.

Envoyer un email de vérification :

Firebase Authentication permet d'envoyer un email de vérification à l'utilisateur actuellement connecté.

Par exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null && !user.emailVerified) {
    await user.sendEmailVerification();
}

Le principe est donc :

Utilisateur connecté
        │
        ▼
Email non vérifié
        │
        ▼
sendEmailVerification()
        │
        ▼
Email envoyé

L'utilisateur devra ensuite consulter sa boîte mail et utiliser le lien fourni à Firebase.

Nous verrons le parcours complet de vérification de l'adresse email dans le module consacré à cette fonctionnalité.

Actualiser les informations de l'utilisateur :

Lorsqu'un utilisateur effectue une action en dehors de l'application, certaines informations peuvent avoir changé.

C'est notamment le cas pour la vérification de l'adresse email.

L'application doit donc parfois demander à Firebase de recharger les informations de l'utilisateur.

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    await user.reload();
}

Après le rechargement, il est possible de récupérer à nouveau l'utilisateur courant :

await FirebaseAuth.instance.currentUser?.reload();

inal updatedUser = FirebaseAuth.instance.currentUser;

if (updatedUser != null) {
    print(updatedUser.emailVerified);
}

Le principe est donc :

Firebase
    │
    ▼
Informations utilisateur
    │
    ▼
reload()
    │
    ▼
Informations actualisées

Cette notion sera importante lorsque nous vérifierons si l'utilisateur a confirmé son adresse email.

Le displayName :

La propriété displayName permet de récupérer le nom affiché de l'utilisateur lorsqu'il est défini.

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print(user.displayName);
}

Cette propriété peut être null.

Par exemple, lors de la création initiale d'un compte avec uniquement une adresse email et un mot de passe :

Email
Mot de passe
      │
      ▼
Compte Firebase
      │
      └── displayName : null

Nous pourrons ensuite permettre à l'utilisateur de définir un nom.

Ce nom pourra également être enregistré dans le profil utilisateur de Firestore.

Il faudra cependant faire la distinction entre :

Firebase Authentication
        │
        └── displayName

Cloud Firestore
        │
        └── Données du profil utilisateur

Ces deux informations peuvent être liées, mais elles ne représentent pas exactement la même responsabilité dans notre architecture.

La photo de profil :

La propriété photoURL permet de récupérer l'adresse d'une éventuelle photo de profil associée à l'utilisateur.

Exemple :

final user = FirebaseAuth.instance.currentUser;
    
if (user != null) {
    print(user.photoURL);
}

Cette propriété peut être null.

Nous n'utiliserons pas immédiatement cette fonctionnalité dans notre projet.

Elle pourra cependant devenir intéressante lorsque nous construirons un véritable profil utilisateur.

Dans ce cas, il faudra également réfléchir à l'endroit où les fichiers seront stockés.

Firebase Storage pourra notamment être utilisé pour gérer les fichiers.

Cette fonctionnalité sera étudiée dans un module ultérieur.

Le numéro de téléphone :

La propriété phoneNumber permet de récupérer le numéro de téléphone associé à l'utilisateur lorsqu'il est disponible.

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print(user.phoneNumber);
}

Cette propriété peut être null.

Dans notre parcours, le numéro de téléphone deviendra important lorsque nous commencerons à mettre en place :

  • l'authentification par SMS;

  • la liaison d'un numéro de téléphone;

  • l'authentification multifacteur;

  • les mécanismes de récupération ou de sécurisation du compte.

Nous ne devons donc pas supposer qu'un utilisateur possède obligatoirement un numéro de téléphone.

Observer l'état d'authentification :

Vérifier currentUser à un instant précis est utile, mais cela ne permet pas de savoir automatiquement lorsqu'un changement intervient.

Firebase Authentication fournit donc des flux permettant d'observer les changements d'état.

Le premier mécanisme que nous allons étudier est :

authStateChanges()

authStateChanges() :

authStateChanges() permet d'écouter les changements concernant l'état d'authentification de l'utilisateur.

Exemple :

FirebaseAuth.instance.authStateChanges().listen((User? user) {
    if (user == null) {
        print('Aucun utilisateur connecté');
    } else {
        print('Utilisateur connecté : ${user.uid}');
    }
});

Nous pouvons représenter son fonctionnement ainsi :

              FirebaseAuth
                   │
                   ▼
          authStateChanges()
                   │
             ┌─────┴─────┐
             │           │
             ▼           ▼
           User         null
             │           │
             ▼           ▼
        Connecté     Déconnecté

Ce mécanisme sera particulièrement important pour notre future architecture de navigation.

Nous pourrons notamment utiliser l'état d'authentification pour déterminer si l'utilisateur doit voir l'écran de connexion ou l'application principale.

Pourquoi utiliser un Stream ?

authStateChanges() retourne un Stream.

Un Stream permet de recevoir des événements au fur et à mesure qu'ils se produisent.

Dans notre cas :

État d'authentification
        │
        ▼
      Stream
        │
        ├── utilisateur connecté
        │
        ├── utilisateur déconnecté
        │
        └── changement d'état

Cela évite de devoir vérifier constamment l'état de l'utilisateur manuellement.

L'application peut simplement écouter le flux.

Exemple avec StreamBuilder :

Flutter permet notamment d'utiliser un StreamBuilder pour construire une interface qui réagit automatiquement aux changements d'un Stream.

Exemple simplifié :

StreamBuilder<User?>(
    stream: FirebaseAuth.instance.authStateChanges(),
    builder: (context, snapshot) {
        if (snapshot.connectionState == ConnectionState.waiting) {
            return const CircularProgressIndicator();
        }

        if (snapshot.hasData) {
            return const Text('Utilisateur connecté');
        }

        return const Text('Utilisateur non connecté');
    },
)

Cet exemple est volontairement simple.

Nous utiliserons plus tard une architecture plus propre avec un AuthGate, des providers et une gestion d'état centralisée.

idTokenChanges() :

Firebase Authentication utilise des jetons d'identification pour représenter l'identité authentifiée auprès des services Firebase.

Firebase propose également :

idTokenChanges()

Ce flux permet d'observer les changements liés à l'état du jeton d'identification.

Exemple :

FirebaseAuth.instance.idTokenChanges().listen((User? user) {
    if (user != null) {
        print('Utilisateur authentifié : ${user.uid}');
    } else {
        print('Aucun utilisateur authentifié');
    }
});

Il est notamment pertinent lorsque le jeton d'identification est renouvelé ou lorsque certaines informations liées à l'identité changent.

Nous verrons plus tard pourquoi cela devient particulièrement intéressant lorsque nous travaillerons avec les rôles et les Custom Claims.

userChanges() :

Firebase fournit également :

userChanges()

Ce flux permet d'observer les modifications concernant l'utilisateur.

Exemple :

FirebaseAuth.instance.userChanges().listen((User? user) {
    if (user != null) {
        print('Informations utilisateur modifiées');
    } else {
        print('Utilisateur déconnecté');
    }
});

Il peut notamment être utile lorsque les propriétés de l'utilisateur changent.

Par exemple :

Utilisateur
     │
     ├── displayName
     ├── photoURL
     ├── email
     ├── emailVerified
     └── autres informations
            │
            ▼
       userChanges()

Différence entre les trois flux :

Il est important de ne pas considérer ces trois méthodes comme identiques.

Nous pouvons retenir leur rôle général de cette manière :

authStateChanges()
        │
        └── État de connexion

idTokenChanges()
        │
        └── État du jeton d'identification

userChanges()
        │
        └── Modifications de l'utilisateur

Dans notre projet, authStateChanges() sera particulièrement important pour savoir si une session existe.

idTokenChanges() et userChanges() pourront être utilisés lorsque nous aurons besoin de réagir à des changements plus spécifiques.

La session :

Lorsqu'un utilisateur se connecte correctement, Firebase Authentication maintient son état d'authentification.

Nous n'avons donc pas besoin de demander à l'utilisateur de saisir son mot de passe à chaque changement d'écran.

Le principe général est :

Utilisateur
     │
     ▼
Connexion
     │
     ▼
Firebase Authentication
     │
     ▼
Session authentifiée
     │
     ▼
Application Flutter

Lorsque l'application redémarre, Firebase peut restaurer l'état d'authentification selon la plateforme et la configuration.

L'application devra donc être capable de gérer le cas où le cas où Firebase est encore en train de déterminer l'état de la session.

C'est notamment pour cette raison que notre future architecture devra prévoir un état de chargement.

Les trois états principaux de l'application :

Lorsque nous construirons notre gestion de l'authentification, nous aurons notamment besoin de distinguer :

Chargement
    │
    ├── Firebase détermine l'état de session
    │
    ▼
Utilisateur connecté
    │
    ou
    ▼
Utilisateur non connecté

Nous pourrons ensuite représenter cela dans l'interface :

                 Authentification
                        │
             ┌──────────┼──────────┐
             │          │          │
             ▼          ▼          ▼
         Chargement   Connecté   Déconnecté
             │          │          │
             ▼          ▼          ▼
          Loader    Application   Login

Cette logique sera à la base du future AuthGate.

La déconnexion :

Pour déconnecter l'utilisateur, Firebase Authentication fournit :

await FirebaseAuth.instance.signOut();

Exemple :

Future<void> logout() async {
    await FirebaseAuth.instance.signOut();
}

Après cette opération, l'utilisateur n'est plus authentifié.

Le currentUser ne représentera alors plus un utilisateur connecté :

final user = FirebaseAuth.instance.currentUser;

if (user == null) {
    print('Utilisateur déconnecté');
}

Le flux authStateChangesr() pourra également signaler ce changement.

Pourquoi ne pas simplement naviguer vers l'écran de connexion ?

Il serait possible de faire quelque chose comme :

Bouton Déconnexion
       │
       ▼
Navigation
       │
       ▼
Écran de connexion

Mais cela ne constitue pas une véritable déconnexion.

Changer d'écran ne supprime pas la session Firebase.

Il faut d'abord effectuer :

await FirebaseAuth.instance.signOut();

Puis laisser l'état d'authentification déterminer l'interface à afficher.

L'architecture correcte sera donc :

Bouton Déconnexion
        │
        ▼
FirebaseAuth.signOut()
        │
        ▼
État d'authentification modifié
        │
        ▼
AuthGate
        │
        ▼
Écran de connexion

Gestion des erreurs :

Les opéerations Firebase Authentication peuvent échouer.

Nous devons donc prévoir une gestion des exceptions.

Firebase fournit notamment FirebaseAuthException.

Exemple :

try {
    // Opération Firebase Authentication
} on FirebaseAuthException catch (e) {
    print('Code : ${e.code}');
    print('Message : ${e.message}');
}

Le code est particulièrement intéressant pour identifier la cause de l'erreur.

Nous pourrons ensuite adapter le message affiché à l'utilisateur.

Exemple de gestion d'une erreur :

try {
    // Connexion ou inscription
} on FirebaseAuthException catch (e) {
    switch (e.code) {
        case 'invalid-credential':
            print('Les identifiants sont incorrects.');
            break;
        default:
            print('Une erreur est survenue.');
    }
}

La liste exacte des codes disponibles dépendra de l'opération effectuée et de l'évolution du SDK.

Il faudra donc toujours se référer à la documentation Firebase correspondant à la version utilisée dans le projet.

Ne pas afficher directement les erreurs techniques :

Il ne faudra pas afficher systématiquement e.message directement dans l'interface.

Par exemple, ceci ne sera pas notre architecture finale :

Text(e.message ?? 'Erreur');

Nous préférerons progressivement avoir une couche permettant de transformer les erreurs Firebase en messages compréhensibles.

Le principe sera :

FirebaseAuthException
        │
        ▼
Code d'erreur
        │
        ▼
Gestionnaire d'erreurs
        │
        ▼
Message utilisateur

Cette approche permettra également de centraliser les traductions et les messages.

Attention aux informations révélées par les erreurs :

La gestion des erreurs doit également respecter les principes de sécurité.

Une application ne doit pas révéler inutilement des informations sensibles.

Par exemple, il faut réfléchir avant d'afficher des messages permettant à une personne extérieure de déterminer précisément si une adresse email possède un compte.

Nous chercherons donc un équilibre message suffisamment clair et protection des informations.

La gestion des erreurs sera approfondie lorsque nous développerons les écrans d'inscription et de connexion.

Firebase Authentication et le mot de passe :

Dans notre architecture, Firebase Authentication sera responsable de la gestion du mot de passe.

Nous ne devons jamais créer notre propre champ permettant d'enregistrer le mot de passe dans Firestore.

Une mauvaise architecture serait :

Firestore
└── users
    └── uid
        ├── email
        ├── password
        └── ...

Nous ne ferons jamais cela.

Nous aurons plutôt :

Firebase Authentication
        │
        ├── Identité
        ├── Email
        ├── Mot de passe
        └── Authentification

Cloud Firestore
        │
        ├── Profil
        ├── Préférences
        └── Données applicatives

Cette séparation est fondamentale.

Relation entre Autehntication et Firestore :

Firebase Authentication et Cloud Firestore ont donc deux responsabilités différentes.

Firebase Authentication permet principalement de gérer : Qui est l'utilisateur ?.

Firestore permet de gérer : Quelles sont les données de l'application ?.

Nous allons utiliser l'UID pour établir une relation entre les deux.

Exemple :

Firebase Authentication
        │
        ▼
UID : abc123
        │
        ▼
Cloud Firestore
        │
        ▼
users/abc123

Nous pourrons donc avoir une structure comme :

users
│
├── abc123
│      ├── displayName
│      ├── createdAt
│      └── preferences
│
├── xyz456
│      ├── displayName
│      ├── createdAt
│      └── preferences
│
└── ...

Nous verrons dans les modules consacrés à Firestore comment créer et protéger ces documents.

Être authentifié ne signie pas avoir tous les droits :

Une erreur fondamentale serait de considérer :

Utilisateur connecté
        =
Accès à toutes les données

Ce n'est pas le fonctionnement que nous voulons.

L'utilisateur peut être correctement authentifié tout en n'ayant pas le droit d'accéder à certaines données.

Nous avons donc :

Authentication
      │
      ▼
Qui es-tu ?
      │
      ▼
UID
      │
      ▼
Security Rules
      │
      ▼
Qu'as-tu le droit de faire ?

Cette distinction entre authentification et autorisation est l'une des notions les plus importantes de tout le syllabus.

Exemple d'autorisation :

Imaginons deux utilisateurs :

Alice → UID_A
Bob   → UID_B

Alice doit pouvoir accéder à ses propres données :

Alice
 │
 └── users/UID_A

Mais elle ne doit pas pouvoir modifier :

users/UID_B

La protection ne doit pas reposer uniquement sur Flutter.

Elle devra être imposée par les Security Rules Firebase.

Nous étudierons cela en détail dans les modules consacrés à Firestore et à la sécurité.

Préparation des rôles utilisateur :

Notre application pourra également avoir différents types d'utilisateurs.

Par exemple :

Utilisateur
Administrateur

Mais nous ne devons jamais sécuriser un rôle uniquement avec une variable locale Flutter.

Si cette information n'est pas contrôlée côté serveur, une architecture dangereuse serait :

bool isAdmin = true;

ou :

if (user.isAdmin) {
    // accès administrateur
}

Le client Flutter peut être manipulé.

Les autorisations importantes devront donc être vérifiées côté Firebase ou côté backend.

Cette notion sera étudiée dans les modules avancés.

Module 4 : Connexion et déconnexion :

Présentation du module :

Nous allons maintenant mettre en place les opérations permettant à un utilisateur déjà inscriot d'accéder à son compte et de terminer sa session.

La connexion et la déconnexion constituent deux opérations fondamentales d'un système d'authentification. Elles doivent être intégrées dans l'application de manière cohérente, en séparant la logique d'authentification de l'interface graphique.

Dans ce module, nous allons utiliser les méthodes fournies par FirebaseAuth pour authentifier un utilisateur à partir de son adresse email et de son mot de passe, puis pour mettre fin à son authentification.

Nous allons également intégrer ces opérations dans le service AuthService introduit précédemment. Cette organisation permettra de conserver une architecture claire et de préparer les modules suivants consacrés à la gestion des sessions, à la navigation et à la protection des écrans.

Objectifs du module :

À la fin de ce module, vous devriez être capable de :

  • distinguer la connexion de l'inscription;

  • utiliser signInWithEmailAndPassword() pour authentifier un utilisateur;

  • comprendre le résultat renvoyé par une tentative de connexion;

  • intégrer la connexion dans AuthService;

  • mettre en place un formulaire de connexion;

  • gérer les erreurs retournées par Firebase Authentication;

  • gérer l'état de chargement pendant une opération d'authentification;

  • utiliser signOut() pour déconnecter l'utilisateur;

  • distinguer la réussite d'une opération d'authentification de la navigation dans l'application.

Différence entre inscription et connexion :

L'inscription et la connexion utilisent toutes deux Firebase Authentication, mais elles répondent à des objectifs différents.

L'inscription permet de créer un nouveau compte. La connexion permet à une personne possédant déjà un compte de s'authentifier.

Ces deux opérations ne doivent donc pas être confondues dans le code de l'application.

Lors d'une inscription, nous utilisons notamment createUserWithEmailAndPassword().

Lors d'une connexion avec une adresse email et un mot de passe, nous utilisons signInWithEmailAndPassword().

Cette seconde méthode ne crée pas un nouveau compte. Elle demande à Firebase Authentication de vérifier les identifiants fournis et d'authentifier l'utilisateur si ceux-ci sont acceptés.

            ▼

            ▼

            │

La méthode signInWithEmailAndPassword() :

La méthode signInWithEmailAndPassword() permet de connecter un utilisateur au moyen de son adresse email et de son mot de passe.

Elle reçoit deux paramètres nommés :

  • email : l'adresse email utilisée pour le compte;

  • password : le mot de passe correspondant.

La méthode renvoie un Future<UserCredential>. Il s'agit donc d'une opération asynchrone : l'application doit attendre son résultat avant de considérer la tentative comme terminée.

Un appel direct à Firebase Authentication peut s'écrire ainsi :

final credential = await FirebaseAuth.instance.signInWithEmailAndPassword(
    email: email,
    password: password,
);

Le mot-clé await permet d'attendre la fin de l'opération asynchrone. Sans cette attente, le code pourrait poursuivre son exécution avant que le résultat de la connexion soit disponible.

Le résultat obtenu est un objet UserCredential. Il permet notamment de récupérer les informations associées à l'authentification qui vient d'être effectuée.

Dans l'architecture de notre projet, nous éviterons cependant de placer cet appel directement dans le bouton du formulaire. Nous allons le centraliser dans AuthService, comme nous l'avons fait pour l'inscription.

Intégration de la connexion dans AuthService :

Le service d'authentification constitue l'intermédiaire entre les écrans Flutter et Firebase Authentication.

Nous allons cmpléter le service existant en lui ajoutant une méthode dédiée à la connexion.

Par exemple :

import 'package:firebase_auth/firebase_auth.dart';

class AuthService {
    final FirebaseAuth _auth = FirebaseAuth.instance;

    Future<UserCredential> signIn({
        required String email,
        required String password,
    }) {
        return _auth.signInWithEmailAndPassword(
            email: email,
            password: password,
        );
    }
}

La méthode signIn() reçoit les identifiants nécessaires et délègue l'opération à Firebase Authentication.

Plusieurs éléments méritent d'être soulignés.

Premièrement, la méthode retourne un Future<UserCredential>. L'appelant peut donc attendre le résultat et réagir à la réussite ou à l'échec de la connexion.

Deuxièmement, le service ne contient pas de loique d'affichage. Il ne décide pas quel message doit apparaître à l'écran et ne manipule pas directement les widgets de l'interface.

Troisièmement, cette méthode ne masque pas les erreurs de Firebase. Elles peuvent être traitées par la couche qui appelle le service, selon les besoins de l'interface.

Nous obtenons ainsi une séparation des responsabilités :

          LoginScreen
               │
               ▼
    AuthService.signIn()
               │
               ▼
FirebaseAuth.signInWithEmailAndPassword()

Cette organisation permet de faire évoluer l'interface sans devoir réécrire la logique d'accès à Firebase.

Si votre AuthService existe déjà dans le projet, il faut ajouter la méthode signIn() à la classe existante plutôt que créer une seconde classe portant le même nom.

  • une zone permettant d'afficher les erreurs éventuelles;

  • un indicateur de chargement pendant la tentative de connexion.

Le formulaire ne doit pas reproduire la logique interne de Firebase Authentication. Son rôle est de recueillir les données, d'effectuer les vérifications élémentaires et d'appeler le service.

Il faut distinguer la validation du formulaire de l'authentification elle-même.

La validation locale permet, par exemple, de vérifier que les champs ne sont pas vides. Elle ne permet pas de déterminer si le compte existe ou si le mot de passe est correct. Ces vérifications relèvent de Firebase Authentication.

Gestion de l'état de chargement :

La connexion étant asynchrone, elle peut prendre un certain temps. L'interface doit donc représenter l'état de l'opération.

Un état de chargement permet notamment :

  • d'informer l'utilisateur que la demande est en cours;

  • d'éviter les clics répétés sur le bouton;

  • de limiter le lancement de plusieurs tentatives simultanées;

  • de rétablir l'interface lorsque l'opération se termine.

Dans un écran utilisant un StatefulWidget, un booléen peut représenter cet état :

bool _isLoading = false;

Au début de l'opération, cet état passe à true. Il revient à false à la fin, que la connexion réussisse ou échoue.

Le bloc finally est adapté à cette situation, car il est exécuté après le bloc try, qu'une exception ait été levée ou non.

Exemple de principe :

Future<void> _signIn() async {
    if (_isLoading) {
        return;
    }

    setState(() {
        _isLoading = true;
    });

    try {
        await _authService.signIn(
            email: _emailController.text.trim(),
            password: _passwordController.text,
        );

        // La connexion a réussi.
        // La suite du parcours sera traitée par l'application.
    } on FirebaseAuthException catch (e) {
        // L'erreur d'authentification sera traitée ici.
    } finally {
        if (mounted) {
            setState(() {
                _isLoading = false;
            });
        }
    }
}

Cet extrait illustre la gestion de l'opération. Il suppose que _authService, _emailController et _passwordController ont été déclarés dans le widget et que le formulaire effectue les validations nécessaires avant l'appel.

La vérification mounted évite d'appeler setState() si le widget a été retiré de l'arbre des widgets pendant l'opération asynchrone.

Dans un écran réel, le bloc de traitement de l'erreur doit également prévoir un retour visible à l'utilisateur. Il ne faut pas laisser un échec de connexion sans explication.

Gestion des erreurs de connexion :

Une tentative de connexion peut échouer pour plusieurs raisons. Par exemple, les identifiants peuvent être incorrects, le compte peut être introuvable ou une limitation temporaire peut empêcher l'opération.
