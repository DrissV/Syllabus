Firebase avec Flutter :

Introduction :

Ce syllabus constitue un parcours complet destiné à accompagner la conception et le développement d'une application Flutter multiplateforme sécurisée, reposant sur les services Firebase.

L'objectif est de construire progressivement une application capable de fonctionner sur Android, iOS et PC/Web, tout en utilisant une infrastructure Firebase commune pour l'authentification, la gestion des utilisateurs, le stockage des données et la sécurité.

La formation commence par la mise en place de l'environnement de développement et la configuration de Firebase. Elle évolue ensuite progressivement vers la création d'un système d'authentification complet et sécurisé.

Une attention particulière est consacrée à la sécurité des comptes utilisateurs. Le parcours comprend notamment :

  • la création d'un compte avec une adresse email et un mot de passe;

  • la vérification de l'adresse email;

  • la vérification du numéro de téléphone par SMS;

  • l'utilisation de l'authentification multifacteur (MFA);

  • l'intégration de Google Authenticator;

  • la gestion des sessions et des différents états d'un compte;

  • la protection des écrans et des fonctionnalités de l'application;

  • la gestion des données avec Cloud Firestore;

  • la mise en place de règles de sécurité Firebase;

  • la gestion des utilisateurs et des administrateurs;

  • la protection contre les accès non autorisés;

  • l'utilisation de Firebase App Check;

  • la mise en place de fonctions backend sécurisées.

Chaque module est conçu pour être suivi progressivement. Les concepts sont expliqués avant leur mise en pratique, puis accompagnés des éléments nécessaires à leur intégration dans le projet : architecture, organisation des fichiers, configuration et code source.

L'objectif final est d'obtenir une application dont la sécurité ne repose pas uniquement sur le code Flutter, mais sur une architecture complète combinant Flutter, Firebase Authentication, Cloud Firestore, Security Rules, App Check et backend sécurisé.

Ce syllabus doit ainsi servir à la fois de cours, de guide de développement et de référence technique, permettant de construire le projet étape par étape et de revenir facilement sur chaque partie lors de son évolution ou de sa maintenance.

Firebase est une plateforme de services backend permettant de fournir à une application différentes fonctionnalités sans devoir développer soi-même l'intégralité de l'infrastructure serveur.

Dans notre projet, Firebase pourra notamment fournir :

Initialisation de Firebase :

Après avoir configuré Firebase, il faut initialiser Firebase au démarrage de l'application.

Le principe sera d'utiliser Firebase Core.

Le fichier main.dart évoluera progressivement.

Exemple :

import 'package:firebase_core/firebase_core.dart';
import 'package:flutter/material.dart';

import 'firebase_options.dart';

Future<void> main() async {
    WidgetsFlutterBinding.ensureInitialized();

    await Firebase.initializeApp(
        options: DefaultFirebaseOptions.currentPlatform,
    );

    runApp(const MyApp());
}

Cette étape est fondamentale.

Elle permet à l'application Flutter d'initialiser Firebase avant d'utiliser les services Firebase.

Pourquoi WidgetsFlutterBinding.ensureInitialized() ?

Avant d'exécuter certaines opérations Flutter asynchrones avant runApp(), il faut s'assurer que le binding est correctement initialisé.

C'est notamment nécessaire dans notre cas puisque nous allons initialiser Firebase avant de lancer l'application.

Le principe est :

Démarrage
   │
   ▼
Initialisation Flutter
   │
   ▼
Initialisation Firebase
   │
   ▼
runApp()
   │
   ▼
Application

Sécurité de la configuration Firebase :

Une confusion fréquente consiste à considérer les informations présentes dans la configuration Firebase comme des secrets.

Il faut distinguer :

Configuration Firebase
        ≠
Secret backend

Certaines informations utilisées pour les applications clientes sont destinées à être distribuées avec l'application.

La sécurité ne doit donc pas reposer sur le fait de cacher simplement la configuration Firebase.

La véritable protection reposera notamment sur :

  • Authentication;

  • Security Rules;

  • App Check;

  • contrôle des permissions;

  • backend sécurisé;

  • gestion correcte des secrets côté serveur.

Cette distinction sera essentielle dans les modules de sécurité.

Ce qui ne doit jamais être placé dans l'application cliente :

Les secrets réellement sensibles ne doivent pas être intégrés directement dans le code Flutter.

Par exemple :

  • clés privées;

  • secrets d'administration;

  • credentials de serveur;

  • clés privées de services backend;

  • tokens permanents privilégiés.

Ces éléments devront être conservés côté serveur ou dans des systèmes adaptés de gestion des secrets.

Authentification : définition :

L'authentification consiste à répondre à la question Qui est cette personne ?

Par exemple, lorsqu'un utilisateur saisit les informations suivantes, l'application doit pouvoir déterminer si ces informations permettent d'identifier correctement un compte.

Email :
alice@example.com

Mot de passe :
********

L'authentification permet donc de vérifier l'identité d'un utilisateur.

Authentification et autorisation :

Il est extrêmement important de ne pas confondre ces deux concepts.

Authentification :

L'authentification répond : Qui es-tu ?.

Exemple :

Utilisateur
   ↓
Connexion
   ↓
Firebase vérifie l'identité
   ↓
Utilisateur authentifié

Autorisation :

L'autorisation répond : Qu'as-tu le droit de faire ?.

Exemple :

Utilisateur authentifié
        │
        ├── Peut lire son profil
        │
        ├── Peut modifier son profil
        │
        └── Ne peut pas modifier le profil d'un autre utilisateur

Cette distinction deviendra essentielle lorsque nous étudierons Firestore Security Rules.

Pourquoi utiliser Firebase Authentication ?

Créer soi-même un système d'authentification sécurisé est une tâche complexe.

Il faut notamment gérer :

  • les mots de passe;

  • le stockage sécurisé des informations;

  • les sessions;

  • les tokens;

  • les renouvellements de tokens;

  • les réinitialisations de mots de passe;

  • la vérification email;

  • les connexions sociales;

  • les numéros de téléphone;

  • la MFA;

  • les protections contre les abus.

Firebase Authentication fournit une infrastructure permettant de gérer une grande partie de ces mécanismes.

FirebaseAuth :

Le point d'accès principal au service Authentication est FirebaseAuth.instance.

On peut considérer cet objet comme le point d'entrée permettant à l'application de communiquer avec Firebase Authentication.

Exemple :

final auth = FirebaseAuth.instance;

Nous pourrons ensuite utiliser auth.currentUser pour récupérer l'utilisateur actuellement authentifié.

L'utilisateur courant :

Une notion essentielle de Firebase Authentication est celle de l'utilisateur actuellement connecté.

Firebase permet de savoir si un utilisateur est actuellement authentifié et, le cas échéant, d'accéder aux informations associées à son compte.

Pour cela, nous utiliserons :

FirebaseAuth.instance.currentUser

Cette propriété retourne l'utilisateur actuellement connecté.

Si aucun utilisateur n'est connecté, la valeur retournée sera null.

On peut donc représenter la situation ainsi :

FirebaseAuth
     │
     ▼
currentUser
     │
 ┌───┴────┐
 │        │
 ▼        ▼
User     null
 │        │
 │        └── Aucun utilisateur connecté
 │
 └── Utilisateur connecté

Un exemple simple serait :

final user =  FirebaseAuth.instance.currentUser;

if (user != null) {
    print('Utilisateur connecté');
} else {
    print('Aucun utilisateur connecté');
}

Cette vérification sera utilisée très fréquemment dans notre application.

Cependant, dans l'architecture finale, nous éviterons de répéter cette logique directement dans chaque écran.

Nous créerons progressivement une gestion centralisée de l'état d'authentification.

La classe User :

Lorsque Firebase Authentication identifie un utilisateur, Flutter peut accéder à un objet de type User.

Cet objet représente l'identité de l'utilisateur authentifié.

Il contient différentes informations utiles.

Par exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print(user.uid);
    print(user.email);
    print(user.displayName);
}

Nous utiliserons principalement ces informations pour identifier l'utilisateur et construire progressivement son profil dans Firestore.

Le UID utilisateur :

Chaque utilisateur Firebase possède un identifiant unique appelé UID.

UID signifie User ID.

Cet identifiant est particulièrement important dans notre architecture.

Utilisateur
     │
     ▼
Firebase Authentication
     │
     ▼
UID
     │
     ▼
Profil Firestore

Nous pourrons ensuite utiliser cet UID pour associer les données Firestore au bon utilisateur.

Par exemple, une structure de données pourra progressivement ressembler à :

├── uid_abc123
│      ├── email
│      ├── displayName
│      └── createdAt
│

│      ├── email
│      ├── displayName
│      └── createdAt
│
└── ...

L'UID est donc une pièce fondamentale de la relation entre Firebase Authentication et Cloud Firestore.

Pourquoi ne pas utiliser l'adresse email comme identifiant ?

Il serait possible de penser que l'adresse email pourrait servir à identifier directement un utilisateur.

Cependant, l'email n'est pas le meilleur identifiant pour notre architecture.

Un utilisateur peut notamment modifier certaines informations de son compte.

L'UID, quant à lui, est l'identifiant unique attribué au compte Firebase.

Nous utiliserons donc principalement :

UID
 │
 ├── Profil utilisateur
 ├── Données personnelles
 ├── Documents Firestore
 └── Autorisations

L'adresse email restera une information associée au compte, mais elle ne remplacera pas l'UID comme identifiant principal de nos données.

Informations principales de l'utilisateur :

L'objet User expose différentes propriétés.

Parmi les plus importantes pour notre projet, on retrouvera notamment :

  • uid : identifiant unique de l'utilisateur;

  • email : adresse email associée au compte;

  • emailVerified : indique si l'adresse email a été vérifiée;

  • displayName : nom affiché lorsqu'il est défini;

  • photoURL : URL éventuelle de la photo de profil;

  • phoneNumber : numéro de téléphone associé au compte lorsqu'il est défini.

On peut accéder à ces informations à partir de l'utilisateur courant :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print('UID : ${user.uid}');
    print('Email : ${user.email}');
    print('Email vérifié : ${user.emailVerified}');
    print('Nom : ${user.displayName}');
    print('Photo : ${user.photoURL}');
    print('Téléphone : ${user.phoneNumber}');
}

Certaines de ces propriétés peuvent être null.

Par exemple, un utilisateur nouvellement créé avec uniquement une adresse email et un mot de passe pourra ne pas avoir de displayName, de photoURL ou de phoneNumber.

Il faut donc toujours tenir compte de cette possibilité dans le code.

Dans notre projet, nous commencerons principalement avec une authentification utilisant une adresse email et un mot de passe.

Cependant, l'architecture doit rester suffisamment flexible pour accueillir d'autres méthodes d'authentification.

Vérifier si l'adresse email a été vérifiée :

La propriété emailVerified permet de savoir si l'utilisateur a confirmé son adresse email.

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    if (user.emailVerified) {
        print('Adresse email vérifiée');
    } else {
        print('Adresse email non vérifiée');
    }
}

Cette propriété retourne une valeur booléenne. Elle peut donc être true ou false.

Le parcours pourra être représenté ainsi :

Compte créé
    │
    ▼
Email non vérifié
    │
    ▼
Envoi du mail de vérification
    │
    ▼
Utilisateur clique sur le lien
    │
    ▼
Email vérifié

Cette étape sera particulièrement importante dans le parcours d'inscription.

Envoyer un email de vérification :

Firebase Authentication permet d'envoyer un email de vérification à l'utilisateur actuellement connecté.

Par exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null && !user.emailVerified) {
    await user.sendEmailVerification();
}

Le principe est donc :

Utilisateur connecté
        │
        ▼
Email non vérifié
        │
        ▼

        │
        ▼

Actualiser les informations de l'utilisateur :

Lorsqu'un utilisateur effectue une action en dehors de l'application, certaines informations peuvent avoir changé.

C'est notamment le cas pour la vérification de l'adresse email.

L'application doit donc parfois demander à Firebase de recharger les informations de l'utilisateur.

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    await user.reload();
}

Après le rechargement, il est possible de récupérer à nouveau l'utilisateur courant :

await FirebaseAuth.instance.currentUser?.reload();

final updatedUser = FirebaseAuth.instance.currentUser;

if (updatedUser != null) {
    print(updatedUser.emailVerified);
}

Le principe est donc :

    │
    ▼
Informations utilisateur
    │
    ▼

    │
    ▼

Cette notion sera importante lorsque nous vérifierons si l'utilisateur a confirmé son adresse email.

Le displayName :

La propriété displayName permet de récupérer le nom affiché de l'utilisateur lorsqu'il est défini.

Exemple :

final user = FirebaseAuth.instance.currentUser;

Cette propriété peut être null.

Par exemple, lors de la création initiale d'un compte avec uniquement une adresse email et un mot de passe :

        └── displayName

        │
        └── Données du profil utilisateur

Ces deux informations peuvent être liées, mais elles ne représentent pas exactement la même responsabilité dans notre architecture.

La photo de profil :

La propriété photoURL permet de récupérer l'adresse d'une éventuelle photo de profil associée à l'utilisateur.

Exemple :

final user = FirebaseAuth.instance.currentUser;

Elle pourra cependant devenir intéressante lorsque nous construirons un véritable profil utilisateur.

Cette fonctionnalité sera étudiée dans un module ultérieur.

Le numéro de téléphone :

La propriété phoneNumber permet de récupérer le numéro de téléphone associé à l'utilisateur lorsqu'il est disponible.

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print(user.phoneNumber);

Cette propriété peut être null.

Dans notre parcours, le numéro de téléphone deviendra important lorsque nous commencerons à mettre en place :

  • l'authentification par SMS;

  • la liaison d'un numéro de téléphone;

  • l'authentification multifacteur;

  • les mécanismes de récupération ou de sécurisation du compte.

Observer l'état d'authentification :

Vérifier currentUser à un instant précis est utile, mais cela ne permet pas de savoir automatiquement lorsqu'un changement intervient.

Firebase Authentication fournit donc des flux permettant d'observer les changements d'état.

Le premier mécanisme que nous allons étudier est :

authStateChanges()

authStateChanges() :

authStateChanges() permet d'écouter les changements concernant l'état d'authentification de l'utilisateur.

Exemple :

FirebaseAuth.instance.authStateChanges().listen((User? user) {
    if (user == null) {
        print('Aucun utilisateur connecté');
    } else {
        print('Utilisateur connecté : ${user.uid}');
    }
});

Nous pouvons représenter son fonctionnement ainsi :

              FirebaseAuth
                   │
                   ▼
          authStateChanges()
                   │
             ┌─────┴─────┐
             │           │
             ▼           ▼
           User         null
             │           │
             ▼           ▼
        Connecté     Déconnecté

Ce mécanisme sera particulièrement important pour notre future architecture de navigation.

Nous pourrons notamment utiliser l'état d'authentification pour déterminer si l'utilisateur doit voir l'écran de connexion ou l'application principale.

Pourquoi utiliser un Stream ?

authStateChanges() retourne un Stream.

Un Stream permet de recevoir des événements au fur et à mesure qu'ils se produisent.

Dans notre cas :

État d'authentification
        │
        ▼
      Stream
        │
        ├── utilisateur connecté
        │
        ├── utilisateur déconnecté
        │
        └── changement d'état

Cela évite de devoir vérifier constamment l'état de l'utilisateur manuellement.

L'application peut simplement écouter le flux.

Exemple avec StreamBuilder :

Flutter permet notamment d'utiliser un StreamBuilder pour construire une interface qui réagit automatiquement aux changements d'un Stream.

Exemple simplifié :

StreamBuilder<User?>(
    stream: FirebaseAuth.instance.authStateChanges(),
    builder: (context, snapshot) {
        if (snapshot.connectionState == ConnectionState.waiting) {
            return const CircularProgressIndicator();
        }

        if (snapshot.hasData) {
            return const Text('Utilisateur connecté');
        }

        return const Text('Utilisateur non connecté');
    },
)

Cet exemple est volontairement simple.

Nous utiliserons plus tard une architecture plus propre avec un AuthGate, des providers et une gestion d'état centralisée.

idTokenChanges() :

Firebase Authentication utilise des jetons d'identification pour représenter l'identité authentifiée auprès des services Firebase.

Firebase propose également :

idTokenChanges()

Ce flux permet d'observer les changements liés à l'état du jeton d'identification.

Exemple :

FirebaseAuth.instance.idTokenChanges().listen((User? user) {
    if (user != null) {
        print('Utilisateur authentifié : ${user.uid}');
    } else {
        print('Aucun utilisateur authentifié');
    }
});

Il est notamment pertinent lorsque le jeton d'identification est renouvelé ou lorsque certaines informations liées à l'identité changent.

Nous verrons plus tard pourquoi cela devient particulièrement intéressant lorsque nous travaillerons avec les rôles et les Custom Claims.

userChanges() :

Firebase fournit également :

userChanges()

Ce flux permet d'observer les modifications concernant l'utilisateur.

Exemple :

FirebaseAuth.instance.userChanges().listen((User? user) {
    if (user != null) {
        print('Informations utilisateur modifiées');
    } else {
        print('Utilisateur déconnecté');
    }
});

Il peut notamment être utile lorsque les propriétés de l'utilisateur changent.

Par exemple :

Utilisateur
     │
     ├── displayName
     ├── photoURL
     ├── email
     ├── emailVerified
     └── autres informations
            │
            ▼
       userChanges()

Différence entre les trois flux :

Il est important de ne pas considérer ces trois méthodes comme identiques.

Nous pouvons retenir leur rôle général de cette manière :

authStateChanges()
        │
        └── État de connexion

idTokenChanges()
        │
        └── État du jeton d'identification

userChanges()
        │
        └── Modifications de l'utilisateur

Dans notre projet, authStateChanges() sera particulièrement important pour savoir si une session existe.

idTokenChanges() et userChanges() pourront être utilisés lorsque nous aurons besoin de réagir à des changements plus spécifiques.

La session :

Lorsqu'un utilisateur se connecte correctement, Firebase Authentication maintient son état d'authentification.

Nous n'avons donc pas besoin de demander à l'utilisateur de saisir son mot de passe à chaque changement d'écran.

Le principe général est :

Utilisateur
     │
     ▼
Connexion
     │
     ▼
Firebase Authentication
     │
     ▼
Session authentifiée
     │
     ▼
Application Flutter

Lorsque l'application redémarre, Firebase peut restaurer l'état d'authentification selon la plateforme et la configuration.

L'application devra donc être capable de gérer le cas où le cas où Firebase est encore en train de déterminer l'état de la session.

C'est notamment pour cette raison que notre future architecture devra prévoir un état de chargement.

Les trois états principaux de l'application :

Lorsque nous construirons notre gestion de l'authentification, nous aurons notamment besoin de distinguer :

Chargement
    │
    ├── Firebase détermine l'état de session
    │
    ▼
Utilisateur connecté
    │
    ou
    ▼
Utilisateur non connecté

Nous pourrons ensuite représenter cela dans l'interface :

                 Authentification
                        │
             ┌──────────┼──────────┐
             │          │          │
             ▼          ▼          ▼
         Chargement   Connecté   Déconnecté
             │          │          │
             ▼          ▼          ▼
          Loader    Application   Login

Cette logique sera à la base du future AuthGate.

La déconnexion :

Pour déconnecter l'utilisateur, Firebase Authentication fournit :

await FirebaseAuth.instance.signOut();

Exemple :

Future<void> logout() async {
    await FirebaseAuth.instance.signOut();
}

Après cette opération, l'utilisateur n'est plus authentifié.

Le currentUser ne représentera alors plus un utilisateur connecté :

final user = FirebaseAuth.instance.currentUser;

if (user == null) {
    print('Utilisateur déconnecté');
}

Le flux authStateChangesr() pourra également signaler ce changement.

Pourquoi ne pas simplement naviguer vers l'écran de connexion ?

Il serait possible de faire quelque chose comme :

Bouton Déconnexion
       │
       ▼
Navigation
       │
       ▼
Écran de connexion

Mais cela ne constitue pas une véritable déconnexion.

Changer d'écran ne supprime pas la session Firebase.

Il faut d'abord effectuer :

await FirebaseAuth.instance.signOut();

Puis laisser l'état d'authentification déterminer l'interface à afficher.

L'architecture correcte sera donc :

Bouton Déconnexion
        │
        ▼
FirebaseAuth.signOut()
        │
        ▼
État d'authentification modifié
        │
        ▼
AuthGate
        │
        ▼
Écran de connexion

Gestion des erreurs :

Les opéerations Firebase Authentication peuvent échouer.

Nous devons donc prévoir une gestion des exceptions.

Firebase fournit notamment FirebaseAuthException.

Exemple :

try {
    // Opération Firebase Authentication
} on FirebaseAuthException catch (e) {
    print('Code : ${e.code}');
    print('Message : ${e.message}');
}

Le code est particulièrement intéressant pour identifier la cause de l'erreur.

Nous pourrons ensuite adapter le message affiché à l'utilisateur.

Exemple de gestion d'une erreur :

try {
    // Connexion ou inscription
} on FirebaseAuthException catch (e) {
    switch (e.code) {
        case 'invalid-credential':
            print('Les identifiants sont incorrects.');
            break;
        default:
            print('Une erreur est survenue.');
    }
}

La liste exacte des codes disponibles dépendra de l'opération effectuée et de l'évolution du SDK.

Il faudra donc toujours se référer à la documentation Firebase correspondant à la version utilisée dans le projet.

Ne pas afficher directement les erreurs techniques :

Il ne faudra pas afficher systématiquement e.message directement dans l'interface.

Par exemple, ceci ne sera pas notre architecture finale :

Text(e.message ?? 'Erreur');

Nous préférerons progressivement avoir une couche permettant de transformer les erreurs Firebase en messages compréhensibles.

Le principe sera :

FirebaseAuthException
        │
        ▼
Code d'erreur
        │
        ▼
Gestionnaire d'erreurs
        │
        ▼
Message utilisateur

Cette approche permettra également de centraliser les traductions et les messages.

Attention aux informations révélées par les erreurs :

La gestion des erreurs doit également respecter les principes de sécurité.

Une application ne doit pas révéler inutilement des informations sensibles.

Par exemple, il faut réfléchir avant d'afficher des messages permettant à une personne extérieure de déterminer précisément si une adresse email possède un compte.

Nous chercherons donc un équilibre message suffisamment clair et protection des informations.

La gestion des erreurs sera approfondie lorsque nous développerons les écrans d'inscription et de connexion.

Firebase Authentication et le mot de passe :

Dans notre architecture, Firebase Authentication sera responsable de la gestion du mot de passe.

Nous ne devons jamais créer notre propre champ permettant d'enregistrer le mot de passe dans Firestore.

Une mauvaise architecture serait :

Firestore
└── users
    └── uid
        ├── email
        ├── password
        └── ...

Nous ne ferons jamais cela.

Nous aurons plutôt :

Firebase Authentication
        │
        ├── Identité
        ├── Email
        ├── Mot de passe
        └── Authentification

Cloud Firestore
        │
        ├── Profil
        ├── Préférences
        └── Données applicatives

Cette séparation est fondamentale.

Relation entre Autehntication et Firestore :

Firebase Authentication et Cloud Firestore ont donc deux responsabilités différentes.

Firebase Authentication permet principalement de gérer : Qui est l'utilisateur ?.

Firestore permet de gérer : Quelles sont les données de l'application ?.

Nous allons utiliser l'UID pour établir une relation entre les deux.

Exemple :

Firebase Authentication
        │
        ▼
UID : abc123
        │
        ▼
Cloud Firestore
        │
        ▼
users/abc123

Nous pourrons donc avoir une structure comme :

users
│
├── abc123
│      ├── displayName
│      ├── createdAt
│      └── preferences
│
├── xyz456
│      ├── displayName
│      ├── createdAt
│      └── preferences
│
└── ...

Nous verrons dans les modules consacrés à Firestore comment créer et protéger ces documents.

Être authentifié ne signifie pas avoir tous les droits :

Une erreur fondamentale serait de considérer :

Utilisateur connecté
        =
Accès à toutes les données

Ce n'est pas le fonctionnement que nous voulons.

L'utilisateur peut être correctement authentifié tout en n'ayant pas le droit d'accéder à certaines données.

Nous avons donc :

Authentication
      │
      ▼
Qui es-tu ?
      │
      ▼
UID
      │
      ▼
Security Rules
      │
      ▼
Qu'as-tu le droit de faire ?

Cette distinction entre authentification et autorisation est l'une des notions les plus importantes de tout le syllabus.

Exemple d'autorisation :

Imaginons deux utilisateurs :

Alice → UID_A
Bob   → UID_B

Alice doit pouvoir accéder à ses propres données :

Alice
 │
 └── users/UID_A

Mais elle ne doit pas pouvoir modifier :

users/UID_B

La protection ne doit pas reposer uniquement sur Flutter.

Elle devra être imposée par les Security Rules Firebase.

Nous étudierons cela en détail dans les modules consacrés à Firestore et à la sécurité.

Préparation des rôles utilisateur :

Notre application pourra également avoir différents types d'utilisateurs.

Par exemple :

Utilisateur
Administrateur

Mais nous ne devons jamais sécuriser un rôle uniquement avec une variable locale Flutter.

Si cette information n'est pas contrôlée côté serveur, une architecture dangereuse serait :

bool isAdmin = true;

ou :

if (user.isAdmin) {
    // accès administrateur
}

Le client Flutter peut être manipulé.

Les autorisations importantes devront donc être vérifiées côté Firebase ou côté backend.

Cette notion sera étudiée dans les modules avancés.

Module 4 : Connexion et déconnexion :

Présentation du module :

Dans le module précédent, nous avons étudié la création d'un compte utilisateur avec Firebase Authentication. Nous allons maintenant mettre en place les opérations permettant à un utilisateur déjà inscriot d'accéder à son compte et de terminer sa session.

La connexion et la déconnexion constituent deux opérations fondamentales d'un système d'authentification. Elles doivent être intégrées dans l'application de manière cohérente, en séparant la logique d'authentification de l'interface graphique.

Dans ce module, nous allons utiliser les méthodes fournies par FirebaseAuth pour authentifier un utilisateur à partir de son adresse email et de son mot de passe, puis pour mettre fin à son authentification.

Nous allons également intégrer ces opérations dans le service AuthService introduit précédemment. Cette organisation permettra de conserver une architecture claire et de préparer les modules suivants consacrés à la gestion des sessions, à la navigation et à la protection des écrans.

Objectifs du module :

À la fin de ce module, vous devriez être capable de :

  • distinguer la connexion de l'inscription;

  • utiliser signInWithEmailAndPassword() pour authentifier un utilisateur;

  • comprendre le résultat renvoyé par une tentative de connexion;

  • intégrer la connexion dans AuthService;

  • mettre en place un formulaire de connexion;

  • gérer les erreurs retournées par Firebase Authentication;

  • gérer l'état de chargement pendant une opération d'authentification;

  • utiliser signOut() pour déconnecter l'utilisateur;

  • distinguer la réussite d'une opération d'authentification de la navigation dans l'application.

Différence entre inscription et connexion :

L'inscription et la connexion utilisent toutes deux Firebase Authentication, mais elles répondent à des objectifs différents.

L'inscription permet de créer un nouveau compte. La connexion permet à une personne possédant déjà un compte de s'authentifier.

Ces deux opérations ne doivent donc pas être confondues dans le code de l'application.

Lors d'une inscription, nous utilisons notamment createUserWithEmailAndPassword().

Lors d'une connexion avec une adresse email et un mot de passe, nous utilisons signInWithEmailAndPassword().

Cette seconde méthode ne crée pas un nouveau compte. Elle demande à Firebase Authentication de vérifier les identifiants fournis et d'authentifier l'utilisateur si ceux-ci sont acceptés.

Le principe général est le suivant :

      Utilisateur
            │
            ▼
 Formulaire de connexion
            │
            ▼
        AuthService
            │
            ▼
 Firebase Authentication
            │
            ▼

L'interface recueille les informations et présente le résultat à l'utilisateur. Le service centralise l'appel à Firebase. Firebase Authentication prend en charge la vérification des identifiants.

La méthode signInWithEmailAndPassword() :

La méthode signInWithEmailAndPassword() permet de connecter un utilisateur au moyen de son adresse email et de son mot de passe.

Elle reçoit deux paramètres nommés :

  • email : l'adresse email utilisée pour le compte;

  • password : le mot de passe correspondant.

La méthode renvoie un Future<UserCredential>. Il s'agit donc d'une opération asynchrone : l'application doit attendre son résultat avant de considérer la tentative comme terminée.

Un appel direct à Firebase Authentication peut s'écrire ainsi :

final credential = await FirebaseAuth.instance.signInWithEmailAndPassword(
    email: email,
    password: password,
);

Le mot-clé await permet d'attendre la fin de l'opération asynchrone. Sans cette attente, le code pourrait poursuivre son exécution avant que le résultat de la connexion soit disponible.

Le résultat obtenu est un objet UserCredential. Il permet notamment de récupérer les informations associées à l'authentification qui vient d'être effectuée.

Dans l'architecture de notre projet, nous éviterons cependant de placer cet appel directement dans le bouton du formulaire. Nous allons le centraliser dans AuthService, comme nous l'avons fait pour l'inscription.

Intégration de la connexion dans AuthService :

Le service d'authentification constitue l'intermédiaire entre les écrans Flutter et Firebase Authentication.

Nous allons cmpléter le service existant en lui ajoutant une méthode dédiée à la connexion.

Par exemple :

import 'package:firebase_auth/firebase_auth.dart';

class AuthService {
    final FirebaseAuth _auth = FirebaseAuth.instance;

    Future<UserCredential> signIn({
        required String email,
        required String password,
    }) {
        return _auth.signInWithEmailAndPassword(
            email: email,
            password: password,
        );
    }
}

La méthode signIn() reçoit les identifiants nécessaires et délègue l'opération à Firebase Authentication.

Plusieurs éléments méritent d'être soulignés.

Premièrement, la méthode retourne un Future<UserCredential>. L'appelant peut donc attendre le résultat et réagir à la réussite ou à l'échec de la connexion.

Deuxièmement, le service ne contient pas de loique d'affichage. Il ne décide pas quel message doit apparaître à l'écran et ne manipule pas directement les widgets de l'interface.

Troisièmement, cette méthode ne masque pas les erreurs de Firebase. Elles peuvent être traitées par la couche qui appelle le service, selon les besoins de l'interface.

Nous obtenons ainsi une séparation des responsabilités :

          LoginScreen
               │
               ▼
    AuthService.signIn()
               │
               ▼
FirebaseAuth.signInWithEmailAndPassword()

Cette organisation permet de faire évoluer l'interface sans devoir réécrire la logique d'accès à Firebase.

Si votre AuthService existe déjà dans le projet, il faut ajouter la méthode signIn() à la classe existante plutôt que créer une seconde classe portant le même nom.

Création du formulaire de connexion :

Le formulaire de connexion permet à l'utilisateur de saisir les informations nécessaires à son authentification.

Il comporte généralement :

  • un champ pour l'adresse email;

  • un champ pour le mot de passe;

  • un bouton de connexion;

  • une zone permettant d'afficher les erreurs éventuelles;

  • un indicateur de chargement pendant la tentative de connexion.

Le formulaire ne doit pas reproduire la logique interne de Firebase Authentication. Son rôle est de recueillir les données, d'effectuer les vérifications élémentaires et d'appeler le service.

Nous pouvons représenter son fonctionnement de la manière suivante :

LoginScreen
    │
    ├── Saisie de l'email
    │
    ├── Saisie du mot de passe
    │
    ├── Validation du formulaire
    │
    ▼
Appel de AuthService.signIn()
    │
    ├── Succès
    │     └── Poursuite du parcours utilisateur
    │
    └── Échec
          └── Affichage d'un message adapté

Il faut distinguer la validation du formulaire de l'authentification elle-même.

La validation locale permet, par exemple, de vérifier que les champs ne sont pas vides. Elle ne permet pas de déterminer si le compte existe ou si le mot de passe est correct. Ces vérifications relèvent de Firebase Authentication.

Gestion de l'état de chargement :

La connexion étant asynchrone, elle peut prendre un certain temps. L'interface doit donc représenter l'état de l'opération.

Un état de chargement permet notamment :

  • d'informer l'utilisateur que la demande est en cours;

  • d'éviter les clics répétés sur le bouton;

  • de limiter le lancement de plusieurs tentatives simultanées;

  • de rétablir l'interface lorsque l'opération se termine.

Dans un écran utilisant un StatefulWidget, un booléen peut représenter cet état :

bool _isLoading = false;

Au début de l'opération, cet état passe à true. Il revient à false à la fin, que la connexion réussisse ou échoue.

Le bloc finally est adapté à cette situation, car il est exécuté après le bloc try, qu'une exception ait été levée ou non.

Exemple de principe :

Future<void> _signIn() async {
    if (_isLoading) {
        return;
    }

    setState(() {
        _isLoading = true;
    });

    try {
        await _authService.signIn(
            email: _emailController.text.trim(),
            password: _passwordController.text,
        );

        // La connexion a réussi.
        // La suite du parcours sera traitée par l'application.
    } on FirebaseAuthException catch (e) {
        // L'erreur d'authentification sera traitée ici.
    } finally {
        if (mounted) {
            setState(() {
                _isLoading = false;
            });
        }
    }
}

Cet extrait illustre la gestion de l'opération. Il suppose que _authService, _emailController et _passwordController ont été déclarés dans le widget et que le formulaire effectue les validations nécessaires avant l'appel.

La vérification mounted évite d'appeler setState() si le widget a été retiré de l'arbre des widgets pendant l'opération asynchrone.

Dans un écran réel, le bloc de traitement de l'erreur doit également prévoir un retour visible à l'utilisateur. Il ne faut pas laisser un échec de connexion sans explication.

Gestion des erreurs de connexion :

Une tentative de connexion peut échouer pour plusieurs raisons. Par exemple, les identifiants peuvent être incorrects, le compte peut être introuvable ou une limitation temporaire peut empêcher l'opération.

Firebase Authentication transmet les erreurs d'authentification au moyen d'exceptions, notamment FirebaseAuthException.

Nous pouvons intercepter cette exception afin de distinguer les principaux cas :

try {
    await _authService.signIn(
        email: email,
        password: password,
    );
} on FirebaseAuthException catch (e) {
    switch (e.code) {
        case 'invalid-credential':
            // Identifants refusés.
            break;
        
        case 'user-not-found':
            // Aucun utilisateur correspondant.
            break;

        case 'wrong-password':
            // Mot de passe incorrect selon le comportement et la configuration du projet.
            break;

        case 'too-many-requests':
            // Trop de tentatives : une ulimitation peut s'appliquer.
            break;
        
        case 'network-request-failed':
            // Problème de communication réseau.
            break;

        default:
            // Erreur non traitée explicitement.
            break;
    }
}

Les codes d'erreur effectivement renvoyés peuvent varier selon la configuration du projet, les fonctionnalités activées et l'évolution de Firebase Authentication. Il faut donc vérifier les codes pris en charge par la version du SDK utilisée.

Il convient également de ne pas supposer que chaque erreur correspond nécessairement à un seul problème métier. Par exemple, Firebase peut regrouper certaines erreurs d'identifiants afin de limiter la divulgation d'informations sur les comptes existants.

Pour cette raison, les messages présentés à l'utilisateur doivent être conçus avec prudence. Un message général tel que Impossible de se connecter avec ces informations peut être préférable à un message confirmant explicitement l'existence ou l'absence d'un compte.

Les détails techniques de l'erreur peuvent être conservés pour le diagnostic, sans exposer inutilement ces informations dans l'interface.

Séparer le traitement technique du message utilisateur :

L'exception reçue de Firebase ne doit pas nécessairement être affichée directement.

La propriété e.code constitue une information technique utile pour le programme. Le texte présenté à l'utilisateur doit, quant à lui, rester compréhensible et adapté au contexte.

Une méthode de traduction des erreurs peut être ajoutée au projet lorsque la gestion des erreurs sera approfondie. À ce stade, le principe essentiel est de séparer :

  • le code technique renvoyé par Firebase;

  • la décision prise par l'application;

  • le message affiché à l'utilisateur.

Cette séparation évite de rendre l'interface dépendante des formulations internes du SDK et facilite la cohérence des messages dans toute l'application.

Mise en place de la déconnexion :

La déconnexion permet de mettre fin à l'authentification courante dans l'application.

Firebase Authentication fournit pour cela la méthode :

FirebaseAuth.instance.signOut();

Cette méthode est aynchrone et renvoie un Future<void>. Il faut donc pouvoir attendre sa fin lorsque le reste du programme dépend du résultat de l'opération.

Comme pour la connexion, nous allons intégrer cette opération dans AuthService.

Nous pouvons compléter la classe précédente de la manière suivante :

import 'package:firebase_auth/firebase_auth.dart';

class AuthService {
    final FirebaseAuth _auth = FirebaseAuth.instance;

    Future<UserCredential> signIn({
        required String email,
        required String password,
    }) {
        return _auth.signInWithEmailAndPassword(
            email: email,
            password: password,
        );
    }

    Future<void> signOut() {
        return _auth.signOut();
    }
}

Dans cet exemple, la méthode signOut() délègue simplement la déconnexion à Firebase Authentication.

La méthode ne retourne pas de UserCredential, puisqu'elle ne produit pas de nouvel objet d'identification. Son type de retour est Future<void>.

L'écran qui déclenche la déconnexion pourra attendre l'opération avant de présenter le résultat approprié.

Déclencher la déconexion depuis l'interface :

La déconnexion est généralement déclenchée par une action explicite par exemple un bouton "Se déconnecter" dans l'écran du compte utilisateur.

Le bouton ne devrait pas contenir directement l'ensemble de la logique Firebase. Il appelle une méthode de l'écran, laquelle utilise AuthService.

Le principe peut être représenté ainsi :

Bouton « Se déconnecter »
           │
           ▼
    Méthode de l'écran
           │
           ▼
   AuthService.signOut()
           │
           ▼
  Firebase Authentication

L'opération doit être attendue à l'aide de await. En cas d'erreur, l'application doit éviter de présenter la déconnexion comme réussie sans avoir traité le résultat de l'opération.

La navigation vers l'écran de connexion ne doit pas non plus être considérée comme la déconnexion elle-même. Changer d'écran ne met pas automatiquement fin à l'authentification Firebase.

Inversement, après une déconnexion effective, l'application doit adapter son interface à l'état d'authentification obtenu. La stratégie générale de navigation sera étudiée dans les modules consacrés à la gestion des sessions, à la protection des écrans et à AuthGate.

Différence entre déconnexion et suppression du compte :

Il est important de distinguer deux opérations.

La déconnexion met fin à l'authentification courante dans l'application. Elle ne supprime pas le compte Firebase Authentication.

La supprssion d'un compte constitue une opération distincte, qui nécessite une méthode spécifique et soulève des questions supplémentaires concernant les données associées à l'utilisateur.

Dans notre projet, le bouton "Se déconnecter" doit donc appeler signOut() et non une méthode de suppression de compte.

Cette distinction est essentielle pour éviter toute perte de compte involontaire.

Connexion réussie et navigation :

Une connexion réussie indique que Firebase Authentication a accepté la tentative d'authentification. Elle ne définit pas, à elle seule, toute la navigation de l'application.

Dans une application simple, il serait possible de naviguer manuellement vers un écran après la connexion. Toutefois, lorsque le projet se développe, cette approche peut entraîner des incohérences : certains écrans peuvent être accessibles alors que l'état d'authentification a changé, ou la navigation peut ne pas refléter correctement une déconnexion.

Nous alons donc séparer progressivement deux responsabilités :

  • l'authentification, qui est prise en charge par Firebase Authentication;

  • la navigation, qui doit réagir à l'état d'authentification de l'application.

Les mécanismes de synchronisation de cet état et de protection des écrans seront étudiés plus tard.

À ce stade, il suffit de retenir qu'un changement de page n'est pas une preuve d'authentification et qu'un écran ne doit pas être considéré comme protégé uniquement parce qu'il est normalement accessible après une connexion.

Points de vigilance :

Lors de l'implémentation de la connexion et de la déconnexion, plusieurs règles doivent être respectées.

  • Ne pas confondre validation et authentification. La validation du formulaire vérifie la cohérence élémentaire des données saisies. Seul le service d'authentification peut déterminer si la tentative est acceptée.

  • Ne pas stocker le mot de passe dans l'application. Le mot de passe est transmis au mécanisme d'authentification lorsque cela est nécessaire. Il ne doit pas être conservé dans des variables persistantes, des fichiers ou des journaux applicatifs.

  • Ne pas ignorer les exceptions. Une erreur doit être traitée de façon à préserver un état cohérent de l'interface et à fournir un retour adapté.

  • Toujours rétablir l'état de chargement. Une opération échouée ne doit pas laisser le bouton désactivé indéfiniment.

  • Ne pas confondre et navigation. Le retour vers un écran public ne remplace pas l'appel à signOut().

  • Ne pas considérer l'interface comme une frontière de sécurité suffisante. La protection des données et des opérations doit également être assurée par les règles et les mécanismes de sécurité des services Firebase concernés.

Module 5 : Vérification de l'adresse email :

Présentation du module :

Lorsqu'un utilisateur crée un compte avec Firebase Authentication, son adresse email n'est pas automatiquement considérée comme vérifiée.

La vérification permet de confirmer que l'utilisateur a accès à l'adresse email qu'il a renseignée lors de son inscription.

Firebase Authentication fournit les méthodes nécessaires pour envoyer un email de vérification et contrôler si l'adresse a été validée.

Objectifs du module :

À la fin de ce module, vous saurez :

  • Envoyer un email de vérification à un utilisateur.

  • Comprendre la propriété emailVerified.

  • Actualiser les informations de l'utilisateur après la vérification.

  • Proposer une action pour renvoyer l'email.

  • Gérer les erreurs et les états de chargement.

  • Comprendre la différence entre l'envoi d'un email et la confirmation effective de l'adresse.

Principe de la vérification email :

Après l'inscription, Firebase crée un compte utilisateur. L'adresse email peut être présente, mais elle n'est pas encore nécessairement vérifiée.

Le processus rrepose principalement sur deux éléments :

  • sendEmailVerification() : demande à Firebase à envoyer un email de vérification.

  • emailVerified : indique si l'adresse email est considérée comme vérifiée par Firebase.

Schéma du parcours :

+--------------------------------+
| emailVerified = false          |
+---------------+----------------+

Point important : l'envoi de l'email ne signifie que l'adresse est déjà vérifiée. La confirmation doit avoir lieu avant que emailVerified passe à true.

Comprendre la propriété emailVerified :

Firebase Authentication expose un objet User représentant l'utilisateur connecté.

Parmi ses propriétés, on retrouve notamment :

Propriété Rôle
uid Identifiant unique de l'utilisateur
email Adresse email de l'utilisateur
emailVerified Indique si l'adresse email est vérifiée

Exemple :

final user = FirebaseAuth.instance.currentUser;

if (user != null) {
    print(user.email);
    print(user.emailVerified);
}

Si emailVerified vaut false, Firebase ne considère pas encore l'adresse comme vérifiée.

Si emailVerified vaut true, l'adresse a été confirmée.

Cette propriété est fournie par Firebase Authentication. Il ne faut pas créer une variable locale indépendante pour remplacer cette information.

Envoyer un email de vérification :

La méthode sendEmailVerification() est disponible sur l'objet utilisateur Firebase.

Exemple simple :

import 'package:firebase_auth/firebase_auth.dart';

Future<void> sendEmailVerification() async {
    final user =  FirebaseAuth.instance.currentUser;

    if (user == null) {
        throw Exception('Aucun utilisateur connecté.');
    }

    if (user.emailVerified) {
        return;
    }

    await user.sendEmailVerification();
}

Explication :

  1. On récupère l'utilisateur actuellement connecté.

  2. On vérifie qu'un utilisateur existe.

  3. On contrôle si son adresse est déjà vérifiée.

  4. Si elle ne l'est pas, on demande à Firebase d'envoyer l'email.

La méthode est asynchrone : l'application doit donc utiliser await et gérer les éventuelles erreurs.

À retenir : cette méthode déclenche l'envoi du message. Elle ne met pas immédiatement emailVerified à true.

Intégrer la vérification dans AuthService :

Pour conserver une architecture organisée, les opérations Firebase Authentication peuvent être regroupées dans le service AuthService.

Ajoute la méthode suivante à la classe existante, sans supprimer les méthodes d'inscription, de connexion ou de déconnexion déjà développées.

import 'package:firebase_auth/firebase_auth.dart';

class AuthService {
    final FirebaseAuth _auth = FirebaseAuth.instance;

    User? get currentUser => _auth.currentUser;

    Future<void> sendEmailVerification() async {
        final user = _auth.currentUser;

        if (user == null) {
            throw Exception('Aucun utilisateur connecté.');
        }

        if (user.emailVerified) {
            return;
        }

        await user.sendEmailVerification();
    }

    Future<bool> reloadAndCheckEmailVerification() async {
        final user = _auth.currentUser;

        if (user == null) {
            return false;
        }

        await user.reload();

        final refreshedUser = _auth.currentUser;

        return refreshedUser?.emailVerified ?? false;
    }
}

Pourquoi utiliser reload() ?

Après avoir cliqué sur le lien reçu par email, l'utilisateur peut revenir dans l'application. L'application User présent en mémoire ne reflète pas nécessairement immédiatement le nouvel état.

L'appel à reload() demande à Firebase d'actualiser les informations du compte.

On récupère ensuite à nouveau currentUser pour lire la valeur actualisée de emailVerified.

Créer un écran de vérification :

Après l'inscription, l'application peut afficher un écran indiquant à l'utilisateur qu'un email de vérification a été envoyé.

Cet écran peut proposer deux actions :

  • Renvoyer l'email de vérification.

  • Vérifier à nouveau si l'adresse a été confirmée.

Exemple d'écran Flutter :

import 'package:flutter/material.dart';
import 'package:firebase_auth/firebase_auth.dart';

    @override
    State<VerifyEmailScreen> createState() => _VerifiyEmailScreenState();

    final FirebaseAuth _auth = FirebaseAuth.instance;

    bool _isSending = false;
    bool _isChecking = false;
    String? _message;

    Future<void> _resendVerificationEmail() async {
        setState(() {
            _isSending = true;
            _message = null;
        });

        try {
            final user = _auth.currentUser;

            if (user == null) {
                setState(() {
                    _message =  'Aucun utilisateur connecté.';
                });
                return;
            }

            await user.sendEmailVerification();

            if (!mounted) {
                return;
            }

            setState(() {
                _message = 'Demande d\'envoi effectuée. Vérifie ta boïte email.';
            });
        } on FirebaseAuthException catch (e) {
            if (!mounted) {
                return;
            }

            setState(() {
                _message = 'Impossible d\'envoyer l\'email (erreur : ${e.code}).';
            });
        } finally {
            if (mounted) {
                setState(() {
                    _isSending = false;
                });
            }
        }
    }

    Future<void> _checkVerification() async {
        setState(() {
            _isChecking = true;
            _message = null;
        });

        try {
            final user = _auth.currentUser;

            if (user == null) {
                setState(() {
                    _message = 'Aucun utilisateur connecté.';
                });
                return;
            }

            await user.reload();

            final refreshedUser = _auth.currentUser;

            if (!mounted) {
                return;
            }

            if (refreshedUser?.emailVerified) {
                setState(() {
                    _message = 'Adresse email vérifiée.';
                });

                // La navigation vers l'écran principal sera intégrée dans le module consacré à la navigation et à AuthGate.
            } else {
                setState(() {
                    _message = 'Adresse non encore vérifiée. Consulte ta boîte email puis réessaie.';
                });
            }
        } on FirebaseAuthException catch (e) {
            if (!mounted) {
                return;
            }

            setState(() {
                _message = 'Erreur lors de la vérification (erreur : ${e.code}).';
            });
        } finally {
            if (mounted) {
                setState(() {
                    _isChecking = false;
                });
            }
        }
    }

                                size: 64,
                            ),
                            const SizedBox(height: 24),
                            const Text(
                                'Vérifie ton adresse email',
                                style: TextStyle(
                                    fontSize: 22,
                                    fontWeight: FontWeight.bold,
                                ),
                                textAlign: TextAlign.center,
                            ),
                            const SizedBox(height: 12),
                            const Text(
                                'Ouvre le message envoyé par Firebase et clique sur le lien de vérification.',
                                textAlign: TextAlign.center,
                            ),
                            const SizedBox(height: 24),
                            SizedBox(
                                width: double.infinity,
                                child: ElevatedButton(
                                    onPressed: _isSending ? null : _resendVerificationEmail,
                                    child: Text(
                                        _isSending ? 'Envoi...' : 'Renvoyer l\'email',
                                    ),
                                ),
                            ),
                            const SizedBox(height: 12),
                            SizedBox(
                                width: double.infinity,
                                child: OutlinedButton(
                                    onPressed: _isChecking ? null : _checkVerification,
                                    child: Text(
                                        _isChecking ? 'Vérification...' : 'J\'ai vérifié mon email',
                                    ),
                                ),
                            ),
                            if (_message != null) ...[
                                const SizedBox(height: 20),

                        ],
                    ),
                ),
            ),
        );

Gestion des erreurs :

L'envoi d'un email ou l'actualisation d'un utilisateur peut échouer.

Il faut intercepter les erreurs Firebase avec FirebaseAuthException.

Exemple :

try {
    await user.sendEmailVerification();
} on FirebaseAuthException catch (e) {
    switch (e.code) {
        case 'too-many-requests':
            // Trop de demandes rapprochées.
            break;
        
        case 'network-request-failed':
            // Problème de connexion réseau.
            break;
        
        default:
            // Traiter les autres erreurs.
            break;
    }

Présentation du module :

Créer le service d'authentification par téléphone :

Pour conserver une architecture claire, les opérations liées à Firebase Authentication peuvent être regroupées dans AuthService.

Ajoute les méthodes suivantes à ton service existant. Si la classe AuthService contient déjà une instance de FirebaseAuth, réutilise-la au lieu de créer plusieurs instances inutiles.

Exemple de service :

import 'package:firebase_auth/firebase_auth.dart';
    
class AuthService {
    final FirebaseAuth _auth = FirebaseAuth.instance;

    String? _verificationId;

    String? get verificationId => _verificationId;

    User? get currentUser => _auth.currentUser;

    Future<void> sendPhoneVerificationCode({
        required String phoneNumber,
        required void Function(String message) onCodeSent,
        required void Function(String message) onError,
        required void Function(PhoneAuthCredential credential) onAutoVerified,
    }) async {
        try {
            await _auth.verifyPhoneNumber(
                phoneNumber: phoneNumber,

                verificationCompleted: (PhoneAuthCredential credential) async {
                    onAutoVerified(credential);
                },

                verificationFailed: (FirebaseAuthException e) {
                    onError(e.code);
                },

                codeSent: (
                    String verificationId,
                    int? resendToken,
                ) {
                    _verificationId = verificationId;
                    onCodeSent(verificationId);
                },

                codeAutoRetrievalTimeout(
                    String verificationId,
                ) {
                    _verificationId = verificationId;
                },
            );
        } on FirebaseAuthException catch (e) {
            onError(e.code);
        } catch (_) {
            onError('unknown-error');
        }
    }

    Future<UserCredential> signInWithSmsCode({
        required String smsCode,
    }) async {
        final verificationId = _verificationId;

        if (verificationId == null) {
            throw Exception(
                'Aucune vérification en cours.',
            );
        }

        final credential = PhoneAuthProvider.credential(
            verificationId: verificationId,
            smsCode: smsCode,
        );

        return await _auth.signInWithCredential(
            credential,
        );
    }
}

Explication :

La méthode sendPhoneVerificationCode() lance la vérification.

Lorsque Firebase appelle codeSent, le service conserve le verificationId. Cet identifiant est nécessaire pour associer le code saisi à la demande de vérification correspondante.

La méthode signInWithSmsCode() construit ensuite un PhoneAuthCredential, puis transmet ce justificatif à Firebase avec signInWithCredential().

Cet exemple illustre la séparation entre le service et l'interface. Dans une application de production, les erreurs, les demandes répétées, les délais d'expiration et le cycle de vie de la vérification doivent être gérés proprement.

Android, iOS et Web : différences importantes :

Le parcours général est similaire, mais les mécanismes techniques diffèrent selon la plateforme.

Android :

Firebase peut effectuer une vérification automatique dans certaines conditions. Selon la configuration et l'appareil, peut s'appuyer sur des mécanismes de vérification de l'application et de récupération du SMS.

La vérification automatique n'est pas garantie : le parcours de saisie manuelle doit rester disponible.

iOS :

La configuration de l'application doit respecter les exigences Firebase pour la vérification téléphonique. APNs et les mécanismes de vérification associés peuvent être nécessaires selon le contexte.

Web :

L'authentification téléphonique Web utilise un mécanisme adapté à la plateforme, notamment reCAPTCHA pour limiter les abus.

Le code Flutter Web doit suivre l'API correspondant à la version du package Firebase utilisée. Ne suppose pas que les mêmes appels de plateforme sont interchangeables partout.

Sécurité et bonnes pratiques :

L'authentification par SMS doit être conçue en tenant compte des risques spécifiques aux numéros de téléphone.

  1. Ne fais pas confiance au numéro simplement parce qu'il a été saisi dans un formulaire.

  2. Ne considère le numéro comme vérifié qu'après validation réussie par Firebase.

  3. Ne conserve pas le code SMS dans une base de données.

  4. Ne journalise pas les codes de vérification ni les informations d'authentification sensibles.

  5. Limite les tentatives et les demandes répétées, et respecte les quotas Firebase.

  6. Ne contourne pas les mécanismes de protection contre les abus.

  7. Prévois un parcours manuel si la vérification automatique ne fonctionne pas.

Comprendre linkWithCredential() :

Avec Firebase Authentication, la méthode linkWithCredential() permet d'associer un fournisseur d'identité à l'utilisateur courant.

Le principe est le suivant :

  1. L'utilisateur est déjà connecté.

  2. L'application demande le numéro de téléphone.

  3. Firebase envoie un SMS de vérification.

  4. L'utilisateur saisit le code reçu.

  5. L'application crée un PhoneAuthCredential.

  6. Ce credential est lié au cmpte existant.

La ligne centrale est :

Ici, user doit être l'utilisateur déjà authentifié, et credential doit correspondre au numéro dont la vérification vient d'être effectuée.

Créer le service de liaison :

Créez le fichier suivant :

lib/features/auth/services/phone_link_service.dart
import 'package:firebase_auth/firebase_auth.dart';

class PhoneLinkService {
    final FirebaseAuth _auth = FirebaseAuth.instance;

    String? _verificationId;

    // Envoie un SMS au numéro à associer au compte.
    Future<void> sendVerificationCode({
        required String phoneNumber,
        required void Function(String verificationId) onCodeSent,
        requited void Function(String message) onError,
    }) async {
        await _auth.verifyPhoneNumber(
            phoneNumber: phoneNumber,

            verificationCompleted: (credential) async {
                try {
                    await _linkCredential(credential);
                } on FirebaseAuthException catch (e) {
                    onError(e.message ?? e.code);
                }
            },

            verificationFailed: (exception) {
                onError(exception.message ?? exception.code);
            },

            codeSent: (verificationId, resendToken) {
                _verificationId = verificationId;
                onCodeSent(verificationId);
            },

            codeAutoRetrievalTimeout: (verificationId) {
                _verificationId = verificationId;
            },
        );
    }

    // Vérifie le code SMS et lie le téléphone au compte existant.
    Future<UserCredential> verifyCodeAndLink({
        required String smsCode,
    }) async {
        final verificationId = _verificationId;

        if (verificationId == null) {
            throw FirebaseAuthException(
                code: 'missing-verification-id',
                message: 'La vérification du numéro doit être lancée.',
            );
        }

        final credential = PhoneAuthProvider.credential(
            verificationId: verificationId,
            smsCode: smsCode,
        );

        return _linkCredential(credential);
    }

    Future<UserCredential> _linkCredential(
        PhoneAuthCredential credential,
    ) async {
        final user = _auth.currentUser;

        if (user == null) {
            throw FirebaseAuthException(
                code: 'no-current-user',
                message: 'Vous devez être connecté pour lier un numéro.';
            );
        }

        return user.linkWithCredential(credential);
    }
}

verifyCodeAndLink() Construit le credential à partir du code reçu.
_linkCredential() Associe le credential au compte Firebase existant.

Comprendre sendPasswordResetEmail() :

La méthode s'utilise de la manière suivante :

await FirebaseAuth.instance.sendPasswordResetEmail(

Le paramètre email correspond à l'adresse à laquelle Firebase doit envoyer les instructions.

La méthode est asynchrone. Elle retourne une Future<void> : elle ne renvoie donc pas directement un objet contenant le nouveau mot de passe ou un lien de réinitialisation.

Il faut attendre son exécution avec await et gérer les éventuelles exceptions.

L'envoi de l'email ne signifie pas que le mot de passe a déjà été modifié. L'utilisateur doit encore suivre les instructions reçues.

Ajouter la méthode dans AuthService :

Nous allons conserver la séparation déjà adoptée dans notre projet : le service gère les opérations Firebase, tandis que l'écran gère la saisie, le chargement et les messages affichés.

}

Module 9 : Gestion du profil utilisateur avec FirebaseAuthentication et Cloud Firestore :

Présentation du module :

Firebase Authentication permet d'identifier les utilisateurs et de gérer leur authentification. Cependant, une application a souvent besoin de stocker des informations supplémentaires, comme le nom, le prénom, la photo de profil ou la date de création du compte.

Pour cela, nous pouvons associer Firebase Authentication à Cloud Firestore.

Firebase Authentication reste responsable de l'identité et des identifiants de connexion, tandis que CloudFirestore permet de conserver les informations complémentaires du profil utilisateur.

Dans ce module, nous allons mettre en place une structure permettant de créer, lire et modifier les données du profil d'un utilisateur.

Objectifs du module :

À la fin de ce module, vous saurez :

  • Comprendre la différence entre authentification et profil utilisateur.

  • Configurer Cloud Firestore dans un projet Flutter.

  • Organiser les données utilisateur dans une collection Firestore.

  • Utiliser l'UID Firebase pour identifier chaque profil.

  • Créer un document utilisateur après l'inscription.

  • Récupérer les informations du profil connecté.

  • Modifier les informations personnelles.

  • Sécuriser l'accès aux données avec les règles Firestore.

Comprendre la différence entre Authentication et Firestore :

Firebase Authentication et Cloud Firestore ont des rôles différents.

Firebase Authentication gère notamment :

  • L'identifiant unique de l'utilisateur, appelé UID.

  • L'adresse email.

  • Les fournisseurs d'authentification associés au compte.

  • L'état d'authentification.

  • Les opérations de connexion et de déconnexion.

Cloud Firestore permet de stocker les informations complémentaires propres à l'application :

  • Le nom et le prénom.

  • La photo de profil.

  • Les préférences de l'utilisateur.

  • La date de création du profil.

  • D'autres informations nécessaires au fonctionnement de l'application.

Il ne faut pas considérer Firestore comme un remplacement de Firebase Authentication. Les deux services sont complémentaires.

Organiser les données utilisateur :

Nous allons créer une collection appelée users.

Chaque document portera l'UID de l'utilisateur correspondant.

La structure sera la suivante :

users
│
├── UID_UTILISATEUR_1
│   ├── firstName
│   ├── lastName
│   ├── email
│   ├── photoUrl
│   └── createdAt
│
└── UID_UTILISATEUR_2
    ├── firstName
    ├── lastName
    ├── email
    ├── photoUrl
    └── createdAt

L'utilisation de l'UID comme identifiant de document présente plusieurs avantages :

  • Chaque utilisateur possède un document identifiable de manière unique.

  • L'application peut retrouver directement le profil du compte connecté.

  • Il n'est pas nécessaire de rechercher le document à partir de l'adresse email.

  • Les règles de sécurité peuvent comparer l'UID du document à celui de l'utilisateur authentifié.

L'UID doit provenir de Firebase Authentication et non d'une valeur choisie librement dans un formulaire.

        required String firstName,
        required String lastName,
    }) async {
        final user = _auth.currentUser;

        if (user == null) {
            throw StateError(
                'Aucun utilisateur authentifié.',
            );
        }

        await _users.doc(user.uid).set({
            'firstName': firstName.trim(),
            'lastName': lastName.trim(),
            'email': user.email,
            'photoUrl': user.photoURL,
            'createdAt': FieldValue.serverTimestamp(),
        });
    }
}

La méthode createProfile() récupère l'utilisateur actuellement authentifié.

Si aucun utilisateur n'est connecté, elle interrompt l'opération. Sinon, elle crée le document correspondant à son UID.

FieldValue.serverTimestamp() permet de demander à Firestore d'enregistrer un horodatage côté serveur.

Cette méthode utilise set() et peut remplacer les données d'un document déjà existant. Pour une création qui ne doit jamais écran un profil existant, il faut vérifier l'existence du document ou utiliser une stratégie de création adapatée.

Créer le profil après l'inscription :

Après la création du compte avec Firebase Authentication, nous pouvons créer le document Firestore correspondant.

Exemple de séquence :

final credential = await FirebaseAuth.instance.createUserWithEmailAndPassword(
    email: email.trim(),
    password: password,
);

final user = credential.user;

if (user == null) {
    throw StateError(
        'Le compte a été créé sans utilisateur disponible.',
    );
}

await UserProfileService().createProfile(
    firstName: firstName,
    lastName: lastName,
);

Dans une application réelle, il faut décider comment traiter le cas où la création du compte Authentication réussit, mais où l'écriture Firestore échoue.

Les deux opérations ne constituent pas une transaction unique : un compte peut donc exister même si son profil Firestore n'a pas été créé.

Une stratégie possible consiste à afficher une erreur récupérable et à permettre de réessayer la création du profil, sans recréer inutilement le compte Authentication.

Récupérer le profil utilisateur :

Pour lire le document associé à l'utilisateur connecté, nous pouvons ajouter cette méthode au service :

Future<Map<String, dynamic>?> getProfile() async {
    final user = _auth.currentUser;

    if (user == null) {
        throw StateError(
            'Aucun utilisateur authentifié.',
        );
    }

    final snapshot = await _users.doc(user.uid).get();

    if (!snapshot.exists) {
        return null;
    }

    return snapshot.data();
}

Cette méthode retourne les données du profil si le document existe. Sinon, elle retourne null.

Il faut distinguer deux situations :

  • Aucun utilisateur n'est connecté.

  • Un utilisateur est connecté, mais son document de profil n'existe pas encore.

Ces deux cas ne doivent pas être traités comme s'ils étaient identiques.

Modifier les informations du profil :

Nous pouvons utiliser update() pour modifier certains champs sans remplacer l'ensemble du document.

Ajoutons cette méthode :

Future<voidégt; updateProfile({
    required String firstName,
    required String lastName,
}) async {
    final user = _auth.currentUser;

    if (user == null) {
        throw StateError(
            'Aucun utilisateur authentifié.',
        );
    }

    await _users.doc(user.uid).update({
        'firstName': firstName.trim(),
        'lastName': lastName.trim(),
    });
}

Contrairement à set(), la méthode update() échoue si le document n'existe pas.

Il faut donc s'assurer que le profil a été créé avant de permettre sa modification.

Cette méthode ne modifie pas l'adresse email de Firebase Authentication. Elle modifie uniquement les données enregistrées dans Firestore.

Si l'adresse email change, il faut également gérer cette modification à travers les méthodes appropriées de Firebase Authentication et maintenir les données du profil cohérentes avec l'état du compte.

Sécuriser les données avec les règles Firestore :

Il ne suffit pas de vérifier dans Flutter que l'utilisateur est connecté. Les règles de sécurité doivent aussi empêcher un utilisateur de lire ou de modifier le profil d'un autre utilisateur.

Une règle de départ pour une collection où chaque utilisateur peut accéder uniquement à son propre document est :

rules_version = '2';
    
service cloud.firestore {
    match /databases/{database}/documents {
        match /users/{userId} {
            allow read, write:
                if request.auth != null && request.auth.uid == userId;
        }
    }
}

Cette règle vérifie que :

  • L'utilisateur est authentifié.

  • L'UID associé à sa session correspond à l'identifiant du document.

Il s'agit d'un exemple pédagogique à adapter avant la mise en production. Il ne valide pas le format des données, les champs autorisés ni les changements possibles. Pour une application réelle, il est préférable de définir séparément les permissions de création, de lecture et de modification, puis de valider les champs et leurs types.

Il ne faut jamais publier une règle autorisant sans restriction la lecture et l'écriture de toute la base de données.

Afficher les informations dans Flutter :

Une fois le profil récupéré, l'écran peut afficher le nom et le prénom de l'utilisateur.

Exemple d'utilisation :

final profileService = UserProfileService();

final profile = await profileService.getProfile();

if (profile != null) {
    final firstName = profile['firstName'] as String? ?? '',

    final lastName = profile['lastName'] as String? ?? '';

    // Utiliser ces valeurs dans l'interface.
}

Dans un widget Flutter, cette lecture asynchrone doit être intégrée à une gestion d'état appropriée, par exemple avec FutureBuilder, un StatefulWidget ou le gestionnaire d'état déjà adopté dans le projet.

Il faut également prévoir un affichage de chargement et un message si le document n'existe pas.

Module 10 : Gestion de l'état d'authentification et des sessions utilisateur :

Présentation du module :

Dans une application Flutter utilisant Firebase Authentication, il est essentiel de savoir si un utilisateur est connecté ou non.

Cette information détermine notamment :

  • L'écran à afficher au démarrage de l'application.

  • L'accès aux pages réservées aux utilisateurs authentifiés.

  • Le comportement de l'application après une connexion.

  • Le retour à l'écran de connexion après une déconnexion.

  • La mise à jour de l'interface lorsque l'état d'authentification change.

Firebase Authentication fournit plusieurs mécanismes permettant d'observer cet état. Nous allons principalement utiliser authStateChanges(), qui émet un événement lorsqu'un utilisateur se connecte ou se déconnecte.

L'objectif est de construire une navigation réactive, capable de s'adapter automatiquement à l'état d'authentification, sans devoir gérer manuellement chaque transition dans tous les écrans.

Objectifs du module :

À la fin de ce module, vous saurez :

  • Comprendre ce qu'est l'état d'authentification.

  • Distinguer l'état de connexion de l'état du profil utilisateur.

  • Utiliser authStateChanges() pour observer les changements.

  • Afficher des écrans différents selon l'état de l'utilisateur.

  • Utiliser StreamBuilder pour construire une interface réactive.

  • Gérer les états de chargement et les erreurs.

  • Protéger les pages nécessitant une authentification.

  • Comprendre le comportement d'une session lors du redémarrage de l'application.

  • Éviter les redirections et les navigations inutiles.

Comprendre l'état d'authentification :

L'état d'authentification représente la présence ou l'absence d'un utilisateur actuellement authentifié.

Dans notre application, nous pouvons distinguer trois situations principales :

  • Utilisateur non connecté : Aucun utilisateur n'est actuellement authentifié. L'application doit afficher les écrans publics, comme la connexion ou l'inscription.

  • Utilisateur connecté : Firebase Authentication fournit un objet User. L'application peut afficher les écrans réservés aux utiisateurs authentifiés.

  • État en cours de détermination : Au démarrage, l'application doit attendre que Firebase fournisse l'état d'authentification. Il est préférable d'afficher un indicateur de chargement plutôt que de montrer brièvement l'écran de connexion à un utilisateur déjà connecté.

Le schéma général est le suivant :

Démarrage de l'application
          │
          ▼
Vérification de l'état Firebase
          │
          ├── Chargement
          │
          ├── Aucun utilisateur
          │         │
          │         ▼
          │    Écran public
          │
          └── Utilisateur connecté
                    │
                    ▼
              Écran principal

Utiliser authStateChanges() :

Firebase Authentication expose la méthode :

FirebaseAuth.instance.authStateChanges()

Cette méthode retourne un Stream<User?>.

Un Stream permet de recevoir des événements au fil du temps. Ici, chaque événement contient soit un utilisateur authentifié, soit null.

Exemple :

import 'package:firebase_auth/firebase_auth.dart';

final FirebaseAuth auth = FirebaseAuth.instance;

Stream<User?> get authStateChanges {
    return auth.authStateChanges();
}

Le flux émet l'état initial de l'authentification, puis les changements liés notamment à la connexion et à la déconnexion.

Il permet donc à l'interface de réagir aux changements sans devoir vérifier manuellement l'état de l'utilisateur après chaque opération.

Comprendre les différents flux Firebase :

Firebase Authentication propose plusieurs flux d'observation. Ils ne répondent pas exactement aux mêmes besoins.

Méthode Fonction principale
authStateChanges() Détecter les connexions et déconnexions.
idTokenChanges() Observer les changements d'état associés au jeton d'identification.
userChanges() Observer les changements concernant l'objet utilisateur, notamment certaines mises à jour de profil.

Pour notre navigation principale, authStateChanges() constitue généralement un bon point de départ.

Si l'application doit réagir à des modifications de profill ou à des mises à jour de jeton, les autres flux peuvent être plus adaptés.

Il faut choisir le flux en fonction du comportement attendu, plutôt que de multiplier les abonnements sans nécessité.

Créer un écran de décision avec StreamBuilder :

Flutter fournit le widget StreamBuilder, qui permet de construire une interface à partir des événements d'un flux.

Nous allons l'utiliser pour déterminer quel écran afficher.

import 'package:firebase_auth/firebase_auth.dart';
import 'package:flutter/material.dart';

class AuthGate extends StatelessWidget {
    const AuthGate({super.key});

    @override
    Widget build(BuildContext context) {
        return StreamBuilder<User?>(
            stream: FirebaseAuth.instance.authStateChanges(),
            builder: (context, snapshot) {
                if (snapshot.connectionState == ConnectionState.waiting) {
                    return const Scaffold(
                        body: Center(
                            child: CircularProgressIndicator(),
                        ),
                    );
                }

                if (snapshot.hasError) {
                    return const Scaffold(
                        body: Center(
                            child: Text(
                                'Impossible de vérifier la session.',
                            ),
                        ),
                    );
                }

                final user = snapshot.data;

                if (user == null) {
                    return const LoginScreen();
                }

                return const HomeScreen();
            },
        );
    }
}

Dans cet exemple, AuthGate agit comme un point de décision :

  • Tant que le flux n'a pas fourni son état initial, un indicateur de chargement est affiché.

  • En cas d'erreur, un message est présenté.

  • Si aucun utilisateur n'est connecté, l'écran de connexion est affiché.

  • Si un utilisateur est connecté, l'écran principal est affiché.

Les classes LoginScreen et HomeScreen représentent les écrans de notre application. Elles doivent être remplacées par les nms réellement utilisés dans le projet.

Intégrer AuthGate dans l'application :

Au lieu de choisir directement l'écran de connexion comme page de démarrage, nous pouvons utiliser AuthGate.

Par exemple :

import 'package:flutter/material.dart';
import 'package:firebase_core/firebase_core.dart';


Future<void> main() async {
    WidgetsFlutterBinding.ensureInitialized();

    await Firebase.initializeApp();

    runApp(const MyApp());
}

class MyApp extends StatelessWidget {
    const MyApp({super.key});

    @override
    Widget build(BuildContext context) {
        return MaterialApp(
            title: 'Mon application',
            home: AuthGate(),
        );
    }
}

Cet exemple suppose que la configuration Firebase nécessaire est déjà présente dans le projet.

Si l'application utilise un fichier de configuration généré par FlutterFire, il faut conserver l'initialisation correspondante.

Avec cette structure, l'écran initial dépend de l'état fourni par Firebase plutôt que d'une décision codée en dur.

Comprendre la persistance de la session :

Firebase Authentication conserve généralement la session de l'utilisateur entre les redémarrages de l'application, selon la plateforme et la configuration utilisée.

Cela signifie qu'un utilisateur qui ferme puis rouvre l'application n'a pas nécessairement besoin de se reconnecter.

Au démarrage, authStateChanges() permet à l'appliation de recevoir l'état d'authentification actuel.

Il faut distinguer deux notions :

  • La persistance de la session : Firebase peut conserver l'état d'authentification.

  • La protection des données : les règles Firebase et les autorisations du backend déterminent les opérations que l'utilisateur peut effectuer.

Le fait qu'un utilisateur soit conecté ne signifie pas qu'il doit pouvoir accéder à toutes les données de l'application.

La durée et le comportement de la session peuvent également dépendre de la plateforme, des paramètres de persistance et des événements de sécurité.

Gérer la déconnexion :

La déconnexion peut être réalisée avec :

await FirebaseAuth.instance.signOut();

Si l'application utilise AuthGate, il n'est généralement pas nécessaire de naviguer manuellement vers l'écran de connexion après cette opération.

Lorsque Firebase émet le nouvel état d'authentification, AuthGate reconstruit l'interface et affiche automatiquement l'écran public.

Exemple de méthode :

Future<void> signOut() async {
    await FirebaseAuth.instance.signOut();
}

Dans l'écran principal, cette méthode peut être appelée depuis un bouton de déconnexion.

Il est recommandé de gérer les éventuelles erreurs et d'empêcher les clics répétés pendant l'opération.

Bonne pratique : éviter de combiner systématiquement signOut() avec plusieurs appels à Navigator.push() ou Navigator.pushReplacement(). Si AuthGate contrôle déjà l'écran affiché, une navigation manuelle supplémentaire peut provoquer des comportements inattendus.

Distinguer authentification et chargement du profil :

Dans le module précédent, nous avons créé un profil utilisateur dans Cloud Firestore.

L'état d'authentification et l'état du profil sont deux informations distinctes.

Un utilisateur peut être connecté alors que son document Firestore :

  • Est en cours de chargement.

  • N'existe pas encore.

  • Ne peut pas être récupéré en raison d'une erreur réseau ou d'autorisation.

Il ne faut donc pas interpréter systématiquement l'absence de profil comme une déconnexion.

Une architecture possible est :

AuthGate
   │
   ├── Aucun utilisateur
   │       │
   │       └── LoginScreen
   │
   └── Utilisateur connecté
           │
           ▼
     Chargement du profil
           │
           ├── Chargement en cours
           │
           ├── Profil disponible
           │
           ├── Profil absent
           │
           └── Erreur de lecture

Cette séparation permet de gérer proprement les comptes dont le profil n'a pas encore été créé.

Protéger les écrans réservés aux utilisateurs connectés :

L'utilisation d'AuthGate permet de choisir l'écran principal, mais elle ne remplace pas les règles de sécurité côté serveur.

Les données Firestore doivent rester protégées par des règles qui vérifient l'identité de l'utilisateur.

De mêm, si l'application utilise une API externe, le serveur doit vérifier le jeton Firebase et les autorisations associées.

Masquer un bouton ou empêcher l'ouverture d'un écran dans Flutter ne constitue pas une protection suffisante des données.

La sécurité doit être appliquée au niveau des services qui donnent accès aux ressources.

Éviter les erreurs fréquentes :

  • Vérifier uniquement currentUser au démarrage :

    FirebaseAuth.instance.currentUser peut être utile pour consulter l'utilisateur actuellement connu par le SDK. Cependant, pour construire une interface réactive qui suit les changements d'état, un flux comme authStateChanges() est généralement plus adapté.

  • Afficher immédiatement l'écran de connexion :

    Cela peut provoquer un affichage temporaire incorrect pendnat que l'état initial est déterminé.

    Il faut prévoir un état de chargement.

  • Créer plusieurs abonnements au même flux :

    Des abonnements inutiles peuvent compliquer la gestion de l'état et rendre le comportement de l'application plus difficile à comprendre.

    Il est préférable d'avoir un point central de décision pour la navigation principale.

  • Confondre déconnexion et suppression du compte :

    signOut() déconnecte l'utilisateur. Il ne supprime ni son compte Firebase Authentication ni son profil Firestore.

    La suppression du compte constitue une opération distincte, avec ses propres règles et précautions.

  • Considérer qu'un utilisateur connecté est toujours autorisé :

    L'authentification établit l'identité. Les autorisations déterminent les actions permises. Ces deux responsabilités doivent rester distinctes.

Module 11 : Gestion des rôles et des autorisations :

Présentation du module :

Dans une application utilisant Firebase Authentication, toues les utilisateurs ne disposent pas nécessairement des mêmes permissions.

Un utilisateur standard peut consulter et modifier ses propres informations, tandis qu'un administrateur peut avoir accès à certaines fonctionnalités supplémentaires, comme la gestion des utilisateurs ou la consultation de données réservées.

Pour mettre en place cette distinction, nous devons séparer trois notions :

  • L'authentification : déterminer qui est l'utilisateur.

  • Le rôle : déterminer à quelle catégorie de permissions il appartient.

  • L'autorisation : déterminer si une action précise est permise.

Firebase Authentication permet d'identifier les utilisateurs. Les règles de sécurité Firestore et, selon les besoins, les revendications personnalisées (custom claims) permettent ensuite de contrôler l'accès aux ressources.

Dans ce module, nous allons mettre en place une gestion des rôles adaptée à une application Flutter utilisant Firebase Authentication et Cloud Firestore.

Objectifs du module :

À la fin de ce module, vous saurez :

  • Comprendre la différence enre authentification et autorisation.

  • Définir des rôles pour les utilisateurs.

  • Distinguer les permissions d'un utilisateur standard de celles d'un administrateur.

  • Comprendre le fonctionnement des custom claims Firebase.

  • Afficher des fonctionnalités différentes selon le rôle.

  • Protéger les données avec les règles de sécurité Firestore.

  • Éviter qu'un utilisateur puisse s'attribuer lui-même des privilèges.

  • Tester les accès autorisés et interdits.

Comprendre le fonctionnement des rôles :

Imaginons une application qui possède deux catégories d'utilisateurs :

  • user : utilisateur standard.

  • admin : administrateur.

Nous pouvons définir les permissions de manière conceptuelle :

Fonctionnalité Utilisateur standard Administrateur
Consulter son profil Oui Oui
Modifier son profil Oui Oui
Consulter les données administratives Non Oui
Gérer les utilisateurs Non Selon les permissions définies
Modifier les rôles Non Seulement si cette opération est explicitement autorisée

Le rôle ne doit pas donner automatiquement accès à toutes les opérations. Il faut déterminer précisément quelles actions chaque catégorie d'utilisateurs peut effectuer.

Le schéma général est le suivant :

Utilisateur
    │
    ▼
Firebase Authentication
    │
    ▼
Identité et UID
    │
    ▼
Rôle et permissions
    │
    ├── Utilisateur standard
    │       │
    │       └── Fonctionnalités autorisées
    │
    └── Administrateur
            │
            └── Fonctionnalités supplémentaires

Pourquoi ne pas gérer les rôles uniquement dans Flutter ?

Une première approche pourrait consister à afficher un bouton uniquement lorsque l'utilisateur est administrateur.

Par exemple :

if (isAdmin) {
    return const AdminButton();
}

Cette condition peut être utile pour adapter l'interface, mais elle ne constitue pas une protection suffisante.

Un utilisateur peut modifier le code de son application, envoyer directement des requêtes ou tenter d'accéder aux données en dehors de l'interface prévue.

Par conséquent, la vérfication du rôle doit également être effectuée par le service qui protège les données.

Dans une application Firebase, les règles de sécurité Firestore peuvent contrôler les accès aux documents, tandis qu'un backend de confiance peut vérifier les permissions avant d'effectuer une opération administrative.

Principe essentiel : l'interface Flutter améliore l'expérience utilisateur, mais la sécurité doit être appliquée côté serveur.

Choisir une stratégie pour stocker les rôles :

Deux approches sont courantes :

  1. Utiliser les custom claims :

    Les custom claims sont des attributs associés au jeton d'identification Firebase de l'utilisateur.

    Nous pouvons, par exemple, associer cette revendication à un compte administrateur :

    {
    "admin": true
}

    Les règles Firestore peuvent ensuite vérifier cette revendication.

    Cette solution est adaptée aux rôles qui contrôlent l'accès à des fonctionnalités sensibles.

    Les custom claims doivent être attribués exclusivement depuis un environnement de confiance, par exemple un backend utilisant le SDK Admin Firebase.

  2. Stocker des informations de rôle dans Firestore :

    Il est également possible d'enregistrer des informations de rôle dans un document utilisateur.

    Par exemple :

    users
└── UID_UTILISATEUR
    ├── firstName
    ├── lastName
    └── preferences

    Dans cette architecture, les informations de profil peuvent rester dans Firestore.

    Cependant, il ne faut pas considérer automatiquement un champ role modifiable par l'utilisateur comme une preuve fiable de ses permissions.

    Si l'application utilise un champ de rôle dans Firestore pour contrôler les accès, les règles doivent empêcher les utilisateurs de modifier eux-mêmes ce champ. La création et la modification des rôles doivent être réalisées par un processus de confiance.

    Pour notre exemple, nous allons utiliser les custom claims pour identifier les administrateurs.

Attribuer un rôle avec le SDK Admin Firebase :

Les revendications personnalisées ne doivent pas être définies directement depuis l'application Flutter.

L'application cliente ne doit pas pouvoir exécuter librement une opération comme :

// À ne pas faire : ce n'est pas une API cliente valide pour attribuer des privilèges administratifs.

L'attribution des rôles doit être réalisée depuis un environnement de confiance utilisant le SDK Admin Firebase, par exemple une fonction backend protégée.

Exemple en Node.js :

const { getAuth } = require("firebase-admin/auth");

async function grantAdminRole(uid) {
    await getAuth().setCustomUserClaims(uid, {
        admin: true,
    });
}

Cet extrait illustre l'opération d'attribution. Il ne doit pas être exposé comme une fonction publique que n'importe quel utilisateur pourrait appeler sans contrôle.

Avant d'attribuer un rôle, le backend doit vérifier que la demande provient d'une personne ou d'un processus autorisé.

Pour retirer le rôle administrateur, le backend peut mettre à jour les revendications du compte en conservant les autres revendications nécessaires :

const { getAuth } = require("firebase-admin/auth");

async function revokeAdminRole(uid) {
    await getAuth().setCustomUserClaims(uid, {
        admin: false,
    });
}

Attention : setCustomUserClaims() remplace l'ensemble des custom claims existantes. Dans une application qui utilise plusieurs revendications, il faut lire les revendications actuelles et construire soigneusement le nouvel objet avant de l'enregistrer.

Il faut également prévoir comment actualiser le jeton du compte concerné pour que les nouvelles revendications soient prises en compte.

Lire le rôle depuis Flutter :

Côté Flutter, nous pouvons récupérer les revendications du jeton de l'utilisateur connecté.

import 'package:firebase_auth/firebase_auth.dart';

Future<bool> isCurrentUserAdmin() async {
    final user = FirebaseAuth.instance.currentUser;

    if (user == null) {
        return false;
    }

    final tokenResult = await user.getIdTokenResult();

    return tokenResult.claims?['admin'] == true;
}

Cette méthode retourne true si le jeton contient la revendication admin avec la valeur booléenne true.

Elle retourne false si aucun utilisateur n'est connecté ou si la revendication n'est pas présente.

Cette vérification peut servir à adapter l'interface Flutter. Elle ne remplace pas les règles de sécurité Firestore ni les vérifications effectuées par le backend.

Si le rôle vient d'être attribué ou retiré, le jeton actuellement détenu par le client peut encore contenir les anciennes revendications.

Dans les situations où une actualisation est nécessaire, Firebase permet de demander un renouvellemet du jeton :

await FirebaseAuth.instance.currentUser?.getIdToken(true);

Cette opération force le renouvellement du jetn. Il faut l'utiliser lorsque cela est nécessaire, et non à chaque reconstruction d'un widget.

Afficher des fonctionnalités selon le rôle :

Nous pouvons maintenant adapter l'interface Flutter en fonction du rôle de l'utilisateur.

Exemple simplifié :

import 'package:flutter/material.dart';

class AdminSection extends StatelessWidget {
    const AdminSection({
        super.key,
        required this.isAdmin,
    });

    final bool isAdmin;

    @override
    Widget build(BuildContext context) {
        if (!isAdmin) {
            return const SizedBox.shrink();
        }

        return ElevatedButton(
            onPressed: () {
                // Ouvrir la section administrative.
            },
            child: const Text(
                'Gestion administrative',
            ),
        );
    }
}

Dans cet exemple, le composant n'affiche le bouton que si isAdmin vaut true.

La valeur doit provenir de la vérification du jeton Firebase, et non d'un champ de formulaire ou d'une préférence modifiable par l'utilisateur.

Dans une application complète, il faut aussi gérer le chargement du rôle et les éventuelles erreurs lors de la récupération du jeton.

Enfin, même si le bouton est masqué, les données administratives doivent rester protégées côté serveur.

Protéger Firestore avec les custom claims :

Les règles Firestore peuvent vérifier la revendication admi directement à partir du jeton d'identification.

Exemple :

rule_version = '2';

service cloud.firestore {
    match /databases/{database}/documets {

        match /users/{userId} {
            allow read: if request.auth != null
                && (
                    request.auth.uid == userId
                    || request.auth.token.admin == true
                );

            allow update: if request.auth != null
                && request.auth.uid == userId;
        }

        match /adminData/{documentId} {
            allow read, write: if request.auth != null
                && request.auth.token.admin == true;
        }
    }
}

Ces règles illustrent deux objectifs :

  • Un utilisateur authentifié peut lire son proppre document utilisateur, tandis qu'un administrateur peut lire les documents de cette collection.

  • La collection adminData est accessible uniquement aux utilisateurs la revendication administrative.

L'exemple ne donne pas aux administrateurs le droit de modifier les documents de tous les utilisateurs dans la collection users, car la règle update ne les y autorise pas.

Cette distinction est volontaire : lire les informations d'un autre utilisateur et modifier ses informations sont deux permissions différentes.

Avant la mise en production, les règles doivent être adaptées à la structure exacte des données et aux opérations réellement nécessaires.

Il faut notamment contrôler les champs modifiables, les types de données et les autorisations de création et de suppression.

Empêcher l'élévation de privilèges :

Une erreur grave consiste à autoriser un utilisateur à modiifier lui-même son rôle.

Par exemple, si un utilisateur peut écrire librement dans son document le champ suivant et que les règles font confiance à ce champ sans contrôle, l'utilisateur peut tenter de s'accorder des privilèges.

{
    "role": "admin"
}

Pour éviter ce problème :

  • Ne jamais laisser le client attribuer des custom claims.

  • Ne pas faire confiance à un champ de rôle modifiable par l'utilisateur.

  • Limiter les opérations administratives à un backend de confiance.

  • Vérifier les permissions avant chaque opération sensible.

  • Tester explicitement les accès refusés.

  • Éviter de confondrela présence d'un bouton administratif avec une véritable autorisation.

Les rôles sont des données de sécurité. Leur modification doit donc suivre un processus contrôlé.

Gérer plusieurs rôles :

Certaines applications nécessitent plus de deux catégories d'utilisateurs.

Par exemple :

  • user : utilisateur standard.

  • moderator : modérateur.

  • admin : administrateur.

Il est possible de représenter certaines permissions sous forme de revendications :

{
    "admin": false,
    "moderator": true
}

Les règles Firestore peuvent ensuite vérifier chaque revendication selon l'opération demandée.

Toutefois, lorsque les permissions deviennent nombreuses, il est préférable de définir clairement une matrice d'autorisationss plutôt que d'ajouter des conditions sans organisation.

Il faut aussi éviter de supposer qu'un rôle implique automatiquement tous les autres. Si un administrateur doit disposer des permissions d'un modérateur, cette relation doit être définie explicitement dans les règles ou le backend.

Comprendre les limites des rôles :

Un rôle ne doit pas être utilisé pour représenter toutes les permissions possibles.

Par exemple, deux utilisateurs standards peuvent avoir des droits différents sur un document précis, même s'ils possèdent le même rôle.

Il faut donc distinguer :

  • Les permissions générales liées au rôle.

  • Les permissions liées à la propriété d'une ressource.

  • Les règles spécifiques à une action.

  • Les éventuelles restrictions liées à l'état du compte.

De plus, les custom claims sont intégrées au jeton d'identification. Leur mise à jour n'est pas nécessairement visible immédiatement dans tous les jetons déjà délivrés.

Pour les opérations sensibles, il faut prévoir une stratégie adaptée à l'actualisation des jetons et à la révocation des accès.

Module 12 : Suppression d'un compte utilisateur et nettoyage des données :

Présentation du module :

Dans une application utilisant Firebase Authentication et Cloud Firestore, un utilisateur doit pouvoir demander la suppression de son compte lorsque cela est nécessaire.

Cette opération ne consiste pas uniquement à supprimer l'utilisateur de Firebase Authentication. L'application peut également avoir enregistré des informations dans Firestore, des fichiers dans Cloud Storage ou d'autres données associées à son UID.

Nous devons donc définir une stratégie de suppression qui tient compte des différents services utilisés par l'application.

Dans ce module, nous allons étudier la suppression d'un compte, la gestion des erreurs, la suppression des données associées et les précautions nécessaires pour éviter de laisser des données orphelines.

Objectifs du module :

À la fin de ce module, vous saurez :

  • Comprendre la différence entre déconnexion et suppression d'un compte.

  • Supprimer un compte avec Firebase Authentication.

  • Gérer les erreurs liées à la suppression.

  • Comprendre la notion de réauthentification.

  • Identifier les données associées à un utilisateur.

  • Supprimer les documents Firestore concernés.

  • Prévoir la suppression des fichiers stockés dans Cloud Storage.

  • Protéger l'opération contre les demandes non autorisées.

  • Éviter les suppressions partielles et les incohérences entre services.

Comprendre les différentes opérations :

Il est important de distinguer trois opérations.

  • La déconnexion :

    La déconnexion termine la session actuelle, mais conserve le compte et ses données.

    await FirebaseAuth.instance.signOut();

  • La suppression du compte Authentication :

    Cette opération supprime le compte d'authentification de Firebase. Elle ne supprime pas automatiquement tous les documents Firestore ou tous les fichiers associés.

  • La suppression complète des données :

    Elle consiste à supprimer les données que l'application doit effacer dans les différents services, conformément à sa politique de conservation et aux obligations applicables.

Le schéma général est le suivant :

Demande de suppression
        │
        ▼
Vérification de l'identité
        │
        ▼
Inventaire des données associées
        │
        ▼
Suppression des données applicatives
        │
        ▼
Suppression du compte Authentication
        │
        ▼
Confirmation du résultat

L'ordre exact dépend de l'architecture. Il faut notamment prévoir ce qui se passe si une étape échoue après que d'autres opérations ont réussi.

Supprimer le compte avec Firebase Authentication :

Firebase Authentication fournit la méthode delete() sur l'objet User.

Exemple :

import 'package:firebase_auth/firebase_auth.dart';

Future<void> deleteAuthAccount() async {
    final user = FirebaseAuth.instance.currentUser;

    if (user == null) {
        throw StateError(
            'Aucun utilisateur authentifié.',
        );
    }

    await user.delete();
}

Cette méthode supprime le compte Firebase Authentication correspondant à l'utilisateur actuellement connecté.

Toutefois, Firebase peut exiger une authentification récente avant d'autoriser cette opération.

Si les identifiants utilisés pour la connexion sont trop anciens, l'appel peut échouer avec l'erreur requires-recent-login.

Dans ce cas, l'application doit demander à l'utilisateur de se réauthentifier, puis lui permettre de recommencer l'opération.

Il ne faut pas contourner cette protection : elle contribue à éviter qu'une personne disposant d'une session laissée ouverte puisse supprimer un compte sans contrôle suffisant.

Comprendre la réauthentification :

La réauthentification consiste à vérifier à nouveau l'identité de l'utilisateur avant une opération sensible.

Elle peut être nécessaire pour des actions comme :

  • La suppression du compte.

  • La modification de certaines informations sensibles.

  • Certaines opérations de sécurité liées aux identifiants.

La méthode à utiliser dépend du fournisseur d'authentification du compte : email et mot de passe, téléphone ou fournisseur externe.

Pour un compte utilisant une adresse email et un mot de passe, une réauthentification peut être réalisée ainsi :

final user = FirebaseAuth.instance.currentUser;

if (user == null || user.email == null) {
    throw StateError(
        'Utilisateur ou adresse email indisponible.',
    );
}

final credential = EmailAuthProvider.credential(
    email: user.email!,
    password: passwordSaisiParUtilisateur,
);

await user.reauthenticateWithCredential(credential);

La variable passwordSaisiParUtilisateur représente le mot de passe saisi dans un formulaire sécurisé. Il ne faut ni le coder en dur ni le stocker durablement dans l'application.

Après la réauthentification réussie, l'application peut relancer l'opération de suppression.

Pour les autres fournisseurs, il faut utiliser le mécanisme de réauthentification correspondant.

Identifier les données associées au compte :

Avant de supprimer un compte, nous devons déterminer quelles données lui appartiennent.

Dans notre architecture, nous avons notamment :

Firebase Authentication
└── UID utilisateur

Cloud Firestore
└── users/{uid}

Cloud Storage
└── Fichiers associés à l'utilisateur

Autres services éventuels
└── Données liées au compte

Le document users/{uid} peut contenir le profil. D'autres collections peuvent contenir des commandes, des publicatios, des messages ou des préférences.

Il ne suffit donc pas de supprimer le document principal du profil pour garantir que toutes les données ont été supprimées.

Il faut établir un inventaire des données et déterminer lesquelles doivent être supprimées, conservées ou anonymisées selon les règles du projet.

Supprimer le document du profil Firestore :

Pour supprimer le document principal du profil, nous pouvons utiliser :

import 'package:cloud_firestore/cloud_firestore.dart';
import 'package:firebase_auth/firebase_auth.dart';

Future>void> deleteUserProfile(String uid) {
    await FirebaseFirestore.instance
            .collection('users')
            .doc(uid)
            .delete();
}

Le paramètre uid doit provenir de l'utilisateur concerné et être contrôlé par l'architecture de sécurité.

Les règles Firestore doivent empêcher un utilisateur de supprimer le profil d'un autre personne.

La suppression d'un document Firestore ne supprime pas automatiquement ses sous-collections. Celles-ci doivent être identifiées et traitées séparément.

Pour des données nombreuses ou imbriquées, un traitement côté serveur est souvent préférable.

Comprendre le problème des suppressions partielles :

Firebase Authentication, Firestore et Cloud Storage sont des services distincts. Une opération exécutée dans l'un ne garantit pas la réussite des opérations effectuées dans les autres.

Imaginons le scénario suivant :

  1. Le document de profil est supprimé.

  2. La suppression du compte Authentication échoue.

  3. L'utilisateur reste authentifié, mais son profil n'existe plus.

Ou, à l'inverse :

  1. Le compte Authentication est supprimé.

  2. La suppression des fichiers échoue.

  3. Des fichiers associés à un UID supprimé restent présents.

Ces situations montrent pourquoi une suppression multi-service doit être conçue comme un processus contrôlé.

Pour une application simple, nous pouvons prévoir des étapes explicites et gérer les erreurs. Pour une application plus complexe, il est préférable de créer un processus de suppression côté serveur avec un état de progression et des tentatives de reprise.

Concevoir un service de suppression :

Pour centraliser la logique, nous pouvons créer un service dédié.

Voici un exemple simplifié pour une application qui ne possède qu'un document de profil à supprimer :

import 'package:cloud_firestore/cloud_firestore.dart';
import 'package:firebase_auth/firebase_auth.dart';

class AccountDeletionService {
    final FirebaseAuth _auth = FirebaseAuth.instance;

    final FirebaseFirestore _firestore = FirebaseFirestore.instance;

    Future<void> deleteAccount() async {
        final user = _auth.currentUser;

        if (user == null) {
            throw StateError(
                'Aucun utilisateur authentifié.',
            );
        }

        final uid = user.uid

        // Cette opération peut nécessiter une réauthentification préalable.
        await user.delete();

        await _firestore
                .collection('users')
                .doc(uid)
                .delete();
    }
}

Cet exemple illustre la séparation dans un service, mais il constitue pas un processus de suppression robuste pour la production.

Si user.delete() réussit et que l'opération Firestore échoue ensuite, le compte est déjà supprimé et l'utilisateur ne peut plus simplement reprendre le processus avec sa session précédente.

Pour une application réelle, il faut envisager un processus de suppression côté serveur, capable de terminer le nettoyage même si le compte Authentication n'existe plus.

Préférer un processus de suppression côté serveur :

Pour une architecture plus robuste, nous pouvons utiliser une fonction backend de confiance.

Le processus peut suivre ces étapes :

  1. Recevoir une demande de suppression authentifiée.

  2. Vérifier l'identité et les permissions de l'utilisateur.

  3. Enregistrer une demande de suppression avec un identifiant de suivi.

  4. Identifier les données associées à l'UID.

  5. Supprimer les documents et ficheiersconcernés.

  6. Supprimer le compte Authentication.

  7. Enregistrer le résultat du processus.

  8. Permettre la reprise du nettoyage en cas d'échec.

La fonction backend doit utiliser les privilèges nécessaires, sans exposer les accès administratifs au client Flutter.

Il faut aussi veiller à ce que la demande de suppression ne puisse pas être déclenchée pour un UID arbitraire fourni par un utilisateur non autorisé.

Dans les systèmes distribués, il est généralement préférable de concevoir le processus pour qu'il puisse être relancé sans causer de dommages supplémentaires. Cette propriété est appelée idempotence.

Par exemple, supprimer un document déjà absent peut être traité comme une étape terminée, tandis qu'une erreur temporaire de stockage peut justifier une nouvelle tentative.

Gérer les erreurs :

Les erreurs doivent être traitées de manière à distinguer les situations que l'utilisateur peut corriger de celles qui nécessitent une intervention technique.

Erreur ou situation Traitement recommandé
requires-recent-login Demander une réauthentification.
user-not-found Vérifier l'état du compte de répéter inutilement la suppression.
network-request-failed Signaler le problème réseau et permettre une reprise adaptée.
Permission Firestore refusée Vérifier les règles et les autorisations prévues
Échec de suppression d'un fichier Enregistrer l'échec et prévoir une nouvelle tentative côté serveur.
Erreur inconnue Afficher un message général et conserver les informations techniques dans des journaux sécurisés.

Il faut éviter d'afficher à l'utilisateur des détails techniques sensibles.

Les journaux ne doivent pas contenir de mots de passe, de jetons d'identification ou d'autres secrets.

Confirmer la suppression dans l'interface :

La suppression d'un compte est une action irréversible dans de nombreux cas. L'interface doit donc demander une confirmation explicite.

Un dialogue peut préciser :

  • Que le compte sera supprimé.

  • Quelles catégories de données seront effacées.

  • Quelles données pourraient être conservées pour des raisons légales ou opérationnelles.

  • Que l'utilisateur devra éventuellement se réauthentifier.

  • Que l'opération peut nécessiter un certain temps.

Le bouton de confirmation ne doit pas annoncer que la suppression est terminée avant que le processus ait réellement ainsi.

Si la suppression s'effectue en arrière-plan, l'application peut afficher un état intermédiaire, par exemple : Votre demande de suppression est en cours de traitement.

Respecter les règles de conservation des données :

La suppression d'un compte doit être cohérente avec la politique de confidentialité de l'application et les obligations légales applicables.

Certaines données peuvent devoir être conservées pendant une période déterminée, selon le contexte de l'application. D'autres doivent être supprimées ou anonymisées.

Il faut donc éviter de supprimer aveuglément toutes les données sans vérifier les règles de conservation applicables.

La stratégie doit être documentée et cohérente entre les différents services.

Module 13 : Gestion des photos de profil et des fichiers :

Présentation du module :

Dans une application Flutter, les utilisateurs peuvent avoir besoin d'ajouter une photo de profil, de remplacer une image existante ou de supprimer un fichier associé à leur compte.

Cloud Firestore permet de stocker des informations textuelles et des métadonnées, mais il n'est généralement pas adapté au stockage direct de fichiers binaires volumineux.

Firebase Storage permer de stocker des fichiers tels que :

  • Les photos de profil.

  • Les images publiées par les utilisateurs.

  • Les documents associés à une fonctionnalité.

  • D'autres fichiers nécessaires à l'application.

Dans ce module, nous allons intégrer Firebase Storage à notre architecture Flutter et apprendre à gérer les fichiers tout en contrôlant les accès.

Objectifs du module :

À la fin de ce module, vous saurez :

  • Comprendre le rôle de Firebase Storage.

  • Configurer Storage dans un projet Firebase.

  • Ajouter les dépendances nécessaires à Flutter.

  • Sélectionner une image depuis l'appareil.

  • Téléverser un fichier vers Firebase Storage.

  • Récupérer l'URL d'un fichier.

  • Enregistrer cette URL dans le profil Firestore.

  • Remplacer et supprimer une photo de profil.

  • Sécuriser les fichiers avec les règles Storage.

  • Gérer les erreurs et les états de chargement.

Comprendre l'architecture :

Nous allons utiliser trois composants complémentaires :

  • Firebase Authentication identifie l'utilisateur et fournit son UID.

  • Firebase Storage conserve les fichiers eux-mêmes.

  • Cloud Firestore conserve les informations de profil et les métadonnées nécessaires à l'application, notamment le chemin ou l'URL de la photo.

L'organisation générale sera la suivante :

Utilisateur connecté
        │
        ▼
Sélection d'une image dans Flutter
        │
        ▼
Firebase Storage
        │
        ├── Stockage du fichier
        │
        └── Récupération de sa référence
                    │
                    ▼
             Cloud Firestore
                    │
                    ▼
           Mise à jour du profil

Il est préférable de ne pas stocker le contenu binaire de l'image dans un document Firestore.

Configurer Firebase Storage :

Dans la console Firebase :

  1. Ouvrir le projet concerné.

  2. Accéder à Firebase Storage.

  3. Initialiser le bucket de stockage si nécessaire.

  4. Vérifier la configuration du projet et les autorisations.

  5. Définir des règles de sécurité adaptées aux fichiers que l'application doit gérer.

Les paramètres disponibles peuvent varier selon le projet et la configuration Firebase. Il faut notamment vérifier les agences de facturation et les restrictions applicables au bucket.

Ajoutons ensuite les dépendances nécessaires :

flutter pub add firebase_storage
flutter pub add image_picker

Le package firebase_storage permet d'interagir avec Firebase Storage. Le package image_picker permet à l'utilisateur de sélectionner une image depuis les sources prises en charge par la plateforme.

Le projet doit déjà être configuré avec Firebase et initialiser correctement Firebase.initializeApp().

Organiser les fichiers dans Storage :

Pour éviter de mélanger les fichiers de différents utilisateurs, nous pouvons organiser les photos de profil à partir de leur UID.

Par exemple :

profile_images/
├── UID_UTILISATEUR_1/
│   └── profile.jpg
└── UID_UTILISATEUR_2/
    └── profile.jpg

Chaque utilisateur dispose ainsi d'un emplacement logique propre à son compte.

Nous pouvons construire le chemin du fichier en utilisant l'UID fourni par Firebase Authentication :

final user = FirebaseAuth.instance.currentUser;

if (user = null) {
    throw StateError('Aucun utilisateur authentifié.');
}

final path = 'profile_images/${user.uid}/profile.jpg';

Le chemin est une référence au fichier dans Storage. Ce n'est pas une URL publique et il ne remplace pas les règles de sécurité.

Sélectionner une image :

Nous pouvons utiiser image_picker pour permettre à l'utilisateur de choisir une photo dans sa galerie.

Exemple de sélection :

import 'package:image_picker/image_picker.dart';

final ImagePicker picker = ImagePicker();

Future<XFile?> pickProfileImage() async {
    reurn picker.pickImage(
        source: ImageSource.gallery,
        imageQuality: 85,
    );
}

La méthode retourne un objet XFile lorsque l'utilisateur sélectionne une image. Si la sélection est annulée, elle retourne null.

Nous devons donc vérifier le résultat avant de poursuivre.

Pour une application complète, il est également recommandé de :

  • Limiter la taille des fichiers acceptés.

  • Vérifier le type de contenu.

  • Prévoir les différences de permissions entre les plateformes.

  • Afficher un aperçu de l'image avant son envoi, si nécessaire.

La sélection d'un fichier ne garantit pas à elle seule que le fichier est sûr ou conforme aux exigences de l'application.

Téléverser une photo vers Firebase Storage :

Une fois l'image sélectionnée, nous pouvons l'envoyer vers Storage.

Exemple de service :

import 'dart:io';

import 'package:firebase_auth/firebase_auth.dart';
import 'package:firebase_storage/firebase_storage.dart';
import 'package:image_picker/image_picker.dart';

class ProfileImageService {
    final FirebaseStorage _storage = FirebaseStorage.instance;

    final FirebaseAuth _auth = FirebaseAuth.instance;

    Future<String> uploadProfileImage(XFile image) async {
        final user = _auth.currentUser;

        if (user == null) {
            throw StateError(
                'Aucun utilisateur authentifié.',
            );
        }

        final reference = _storage
                            .ref()
                            .child('profile_images')
                            .child(user.uid)
                            .child('profile.jpg');
        
        await reference.putFile(
            File(image.path),
            SettableMetadata(
                contentType: 'image/jpeg',
            ),
        );

        return reference.getDownloadURL();
    }
}

Cet exemple utilise dart:io et convient aux plateformes qui prennent en charge les fichiers locaux avec cerre API. Pour une application Flutter Web, il faut utiliser une approche compatible avec le Web, par exemple l'envoi des octets du fichier avec putData().

Le image/jpeg doit correspondre au format réel du fichier. Si l'application accepte plusieurs formats, elle doit déterminer le type approprié au lieu de déclarer systématiquement que tous les fichiers sont des JPEG.

La méthode retourne l'URL de téléchargement une fois le téléversement terminé.

Enregistrer la photo dans le profil Firestore :

Après le téléversement, nous pouvons mettre à jour le document de profil pour enregistrer l'URL de la photo.

Exemple :

import 'package:cloud_firestore/cloud_firestore.dart';
import 'package:firebase_auth/firebase_auth.dart';

Future<void> updateProfilePhotoUrl(
    String photoUrl,
) async {
    final user = FirebaseAuth.instance.currentUser;

    if (user == null) {
        throw StateError(
            'Aucun utilisateur authentifié.',
        );
    }

    await FirebaseFirestore.instance
            .collection('users')
            .doc(user.id)
            .update({
                'photoUrl': photoUrl,
            });
}

Nous pouvons ensuite utiliser cette information dans l'interface Flutter pour afficher la photo.

Il est également possible de stocker le chemin Storage plutôt que l'URL de téléchargement, puis de demander une URL lorsque l'application en a besoin.

Cette seconde approche peut faciliter la gestion des références au fichier. Une URL de téléchargement Firebase peut fonctionner comme un lien porteur d'accès : il faut donc éviter de la diffuser sans précaution.

Afficher la photo de profil :

Lorsque le profil contient une URL accessible, Flutter peut afficher l'image avec Image.network().

Image.network(
    photoUrl,
    width: 100,
    height: 100,
    fit: BoxFit.cover,
    errorBuilder: (context, error, stackTrace) {
        return const Icon(
            Icons.account_circle,
            size: 100,
        );
    },
)

L'option errorBuilder permet d'afficher une icône de remplacement si l'image ne peut pas être chargée.

Dans une interface de profil,nous pouvons également utiliser CircleAvatar pour obtenir un affichage circulaire.

Il faut prévoir un état de chargement et un affichage de remplacement lorsque l'utilisateur ne possède pas encore de photo.

Remplacer une photo existante :

Dans notre exemple, chaque utilisateur utilise le chemin profile.jpg.

Le téléversement d'une nouvelle image à ce même emplacement remplace le fichier existant, si les règles et les permissions l'autorisent.

La procédure générale est la suivante :

  1. Sélectionner la nouvelle image.

  2. Vérifier qu'elle respecte les contraintes de l'application.

  3. Téléverser le nouveau fichier.

  4. Récupérer sa référence ou son URL.

  5. Mettre à jour le profil Firestore.

  6. Gérer les éventuelles erreurs.

Il faut réfléchir au comportement en cas d'échec partiel. Par exemple, si l'image est téléversée mais que la mise à jour Firestore échoue, le fichier existe alors que le profil peut encore référencer l'ancienne URL.

Pour une application plus robuste, nous pouvons utiliser des noms de fichiers versionnés, mettre à jour le profil après le téléversement, puis supprimer l'ancien fichier lorsque la nouvelle photo est correctement enregistrée.

Cette approche réduit le risque de perdre l'ancienne photo avant que la nouvelle soit disponible.

Supprimer une photo de profil :

Firebase Storage permet de supprimer un fichier à partir de sa référence.

Exemple :

Future<void> deleteProfileImage() async {
    final user = FirebaseAuth.instance.currentUser;

    if (user == null) {
        throw StateError(
            'Aucun utilisateur authentifié.',
        );
    }

    final reference = FirebaseStorage.instance
                        .ref()
                        .child('profile_images')
                        .child(user.uid)
                        .child('profile.jpg');

    await reference.delete();

    await FirebaseFirestore.instance
            .collection('users')
            .doc(user.uid)
            .update({
                'photoUrl': FieldValue.delete(),
            });

}

Cette méthode supprime le fichier puis retire le champ photoUrl du document utilisateur.

Elle suppose que le document de profil existe et que le fichier est présent. Si le fichier a déjà été supprimé, l'opération peut échouer : il faut donc prévoir une gestion des erreurs et un traitement adapté aux fichiers absents.

Comme les deux opérations ne constituent pas une transaction commune, il faut aussi prévoir le cas où la suppression du fichier réussit mais où la mise à jour Firestore échoue.

Sécuriser Firebase Storage :

Les règles Storage doivent empêcher un utilisateur de modifier les fichiers d'un autre compte.

Pour les photos de profil, une règle de départ peut être :

rules_version = '2';

service firebase.storage {
    match /b/{bucket}/o {
        match /profile_images/{userId}/{fileName} {
            allow read: if request.auth != null;

            allow write: if request.auth != null
                && request.auth.uid == userId
                && request.resource.size < 5 * 1024 * 1024
                && request.resource.contentType.matches(
                    'image/.*'
                );
        }
    }
}

Cette règle illustre les contrôles suivants :

  • L'utilisateur doit être authentifié pour écrire.

  • L'UID de la session doit correspondre à l'utilisateur du chemin.

  • La taille du fichier doit être inférieure à 5 Mo.

  • Le type de contenu déclaré doit commencer par image/.

Cette règle est un point de départ, pas une garantie complète de validation de l'image. Le type MIME peut être déclaré par le client et ne prouve pas à lui seul que le contenu est une image valide.

Il faut également remarquer que request.resource peut être absent lors d'une suppression. Une règle de production doit traiter explicitement les créations, les modifications et les suppressions afin de ne pas bloquer accidentellement les opérations nécessaires.

Si les photos ne doivent être visibles que par leur propriétaire, la règle de lecture doit également vérifier que l'UID de l'utilisateur connecté correspond à celui du chemin.

Les règles doivent être testées avec les cas d'accès autorisé et interdit.

Gérer les erreurs et le chargement :

Le téléversement peut échouer pour plusieurs raisons :

  • Absence de connexion Internet.

  • Fichier trop volumineux.

  • Permissions insuffisantes.

  • Règles Storage qui refusent l'opération.

  • Fichier local devenu indisponible.

  • Erreur lors de la mise à jour Firestore.

L'interface doit afficher un indicateur de progression ou de chargement et empêcher les demandes répétées pendant une opération en cours.

Il est aussi possible d'écouter l'état du téléversement :

final task = reference.putFile(file);

task.snapshotEvents.listen((snapshot) {
    final total = snapshot.totalBytes;
    final transferred = snapshot.bytesTransferred;

    if (total > 0) {
        final progress = transferred / total;
        // Transmettre la progession à l'interface.
    }
});

Dans un widget réel, il faut gérer l'abonnement au flux et sa durée de vie correctement, afin d'éviter des abonnements inutiles ou des mises à jour d'état après la destruction du widget.

Module 14 : Validation des données utilisateur et gestion des erreurs :

Présentation du module :

Dans une application Flutter connectée à Firebase, les utilisateurs peuvent saisir des informations incorrectes, oublier des champs obligatoires ou tenter d'envoyer des données qui ne respectent pas les règles de l'application.

Pour garantir la fiabilité et la sécurité de l'application, il est nécessaire de mettre en place une validation des données et une gestion appropriée des erreurs.

Objectifs du module :

Dans ce module, vous allez apprendre à :

  • Valider les formulaires dans Flutter.

  • Vérifier les données avant de les envoyer à Firebase.

  • Gérer les erreurs de Firebase Authentication.

  • Contrôler les données enregistrées dans Cloud Firestore.

  • Sécuriser les écritures avec les règles Firebase.

  • Afficher des messages d'erreur compréhensibles.

  • Éviter de considérer la validation côté client comme une mesure de sécurité suffisante.

Comprendre les différents niveaux de validation :

La validation des données doit être réalisée à plusieurs niveaux.

  1. Validation côté Flutter :

    Elle permet de vérifier rapidement les informations saisies par l'utilisateur avant d'effectuer une opération.

    Exemples :

    • Vérifier qu'un champ obligatoire n'est pas vide.

    • Vérifier le format d'une adresse email.

    • Vérifier la longueur minimale d'un mot de passe.

    • Vérifier que deux mots de passe correspondent.

  2. Validation côté Firebase :

    Firebase Authentication applique ses propres contraintes aux opérations d'authentification. Les règles de sécurité Firestore et Storage permettent également de contrôler les opérations autorisées sur les données.

    Ces contrôles sont essentiels, car un utilisateur peut contourner les formulaires Flutter et tenter d'effectuer des opérations directement sur les services Firebase.

  3. Validation côté serveur :

    Certaines règles métier complexes doivent être exécutées dans un environnement de confiance, par exemple avec Cloud Functions.

    Exemples :

    • Vérifier qu'un code d'invitation est valide.

    • Contrôler une opération qui nécessite plusieurs vérifications.

    • Attribuer un rôle privilégié après validation par un service de confiance.

    Règle essentielle : la validation Flutter améliore l'expérience utilisateur, mais ne remplace jamais les contrôles de sécurité côté serveur.

Créer un formulaire avec validation Flutter :

Flutter fournit les widgets Form, TextFormField et la propriété validator pour valider les champs.

Exemple complet :

Créons un formulaire qui demande un nom et une adresse email.

import 'package:flutter/material.dart';

class RegistrationForm extends StatefulWidget {
    const RegistrationForm({super.key});

    @override
    State<RegistrationForm> createState() => _RegistrationFormState();
}

class _RegistrationFormState extends State<RegistrationForm> {
    final _formKey = GlobalKey<FormState>();

    final _nameController = TextEditingController();
    final _emailController = TextEditingController();

    @voverride
    void dispose() {
        _nameController.dispose();
        _emailController.dispose();
        super.dispose();
    }

    String? validateName(String? value) {
        if (value == null || value.trim().isEmpty) {
            return 'Le nom est obligatoire.';
        }

        if (value.trim().length < 2) {
            return 'Le nom doit contenir au moins 2 caractères.';
        }

        return null;
    }

    String? validateEmail(String? value) {
        final email = value?.trim() ?? '';
        
        if (email.isEmpty) {
            return 'L\'adresse email est obligatoire.';
        }

        final emailRegex = RegExp(r'^[^@\s]+\[^@\s]+.[^@\s]+$');

        if (!emailRegex.hasMatch(email)) {
            return 'Veuillez saisir une adresse email valide.';
        }

        return null;
    }

    void submitForm() {
        if (!_formKey.currentState!.validate()) {
            return;
        }

        final name = _nameController.text.trim();
        final email = _emailController.text.trim();

        ScaffoldMessenger.of(context).showSnackBar(
            SnackBar(
                content: Text('Formulaire valide pour $name ($email)'),
            ),
        );

        // Le formulaire est valide.
        // Une opération Firebase pourra être exécutée ici.
    }

    @override
    Widget build(BuildContext context) {
        return Form(
            key: _formKey,
            child: Column(
                children: [
                    TextFormField(
                        controller: _nameController,
                        decoration: const InputDecoration(
                            labelText: 'Nom',
                            border: OutlineInputBorder(),
                        ),
                        validator: validateName,
                    ),
                    const SizedBox(height: 16),
                    TextFormField(
                        controller: _emailController,
                        keyboardType: TextInputType.emailAddress,
                        decoration: const InputDecoration(
                            labelText: 'Adresse email',
                            border: OutlineInputBorder(),
                        ),
                        validator: validateEmail,
                    ),
                    const SizedBox(height: 20),
                    ElevatedButton(
                        onPressed: submitForm,
                        child: const Text('Valider'),
                    ),
                ],
            ),
        );
    }
}

Fonctionnement :

La méthode validate() exécute les validateurs de champs du formulaire.

Si au moins un champ renvoie un message d'erreur, la validation échoue et les messages correspondants sont affichés.

Si tous les validateurs renvoient null, le formulaire est considéré comme valide.

La validation de l'adresse email présentée ici est volontairement simple. Elle permet de détecter les formats manifestement incorrects, mais ne garantit pas que l'adresse existe ou qu'elle appartient à l'utilisateur.

Valider un mot de passe :

Une application peut définir des critères de mot de passe adaptés à ses besoins.

Voici un exemple de validation avec une longueur minimale :

String? validatePassword(String? value) {
    if (value == null || value.isEmpty) {
        return 'Le mot de passe est obligatoire.';
    }

    if (value.length < 8) {
        return 'Le mot de passe doit contenir au moins 8 caractères.';
    }

    return null;
}

Si l'application demande une confirmation du mot de passe, il faut aussi comparer les deux valeurs.

String? validatePasswordConfirmation(
    String? value,
    String password,
) {
    if (value == null || value.isEmpty) {
        return 'Veuillez confirmer le mot de passe.';
    }

    if (value != password) {
        return 'Les mots de passe ne corresponden pas.';
    }

    return null;
}

Ces contrôles améliorent l'expérience utilisateur. Les politiques de mot de passe configurées dans Firebase Authentication et les protections disponibles dans le projet doivent également être prises en compte.

Ne stockez jamais les mots de passe en clair dans Firestore.

Gérer les erreurs de Firebase Authentication :

Les opérations Firebase peuvent échouer même lorsque le formulaire est valide.

Les causes possibles comprennent :

  • Une adresse email déjà utilisée.

  • Un mot de passe qui ne respecte pas les exigences configurées.

  • Une connexion Internet indisponible.

  • Des identifiants incorrects.

  • Une opération qui nécessite une nouvelle authentification.

  • Une configuration Firebase incorrecte.

Flutter permet d egérer ces erreurs avec try, on et catch.

Exemple lors de la création d'un compte :

import 'package:firebase_auth/firebase_auth.dart';
    
Future<String?> createAccount(
    String email,
    String password,
) async {
    try {
        await FirebaseAuth.instance.createUserWithEmailAndPassword(
            email: email.trim(),
            password: password,
        );

        return null;
    } on FirebaseAuthException catch (e) {
        switch (e.code) {
            case 'email-already-in-use':
                return 'Cette adresse email ne peut pas être utilisée.';
            case 'invalid-email':
                return 'Le format de l\'adresse email est incorrect.';
            case 'weak-password':
                return 'Le mot de passe ne respecte pas les exigences.';
            case 'network-request-failed':
                return 'Connexion impossible. Vérifiez votre réseau.';
            default:
                return 'Impossible de créer le compte pour le moment.';
        }
    } catch (_) {
        return 'Une erreur inattendue est survenue.';
    }
}

Cette fonction renvoie null en cas de succès et un message en cas d'erreur.

Exemple d'utilisation dans un bouton :

final error = await createAccount(
    emailController.text,
    passwordController.text,
);

if (!context.mounted) {
    return;
}

if (error != null) {
    ScaffoldMessenger.of(context).showSnackBar(
        SnackBar(content: Text(error)),
    );
}

Dans une application réelle, prévoyez également un état de chargement afin d'éviter les clics multiples pendant une requête.

Les codes d'erreur disponibles peuvent évoluer selon l'opération et la configuration. Il faut donc adapter les cas traités à la version de Firebase utilisée.

Gérer les erreurs lors d'une écriture Firestore :

Cloud Firestore peut refuser une écriture lorsque les règles de sécurité ne l'autorisent pas, lorsque le réseau est indisponible ou lorsqu'une autre erreur survient.

Exemple :

import 'package:cloud_firestore/cloud_firestore.dart';
import 'package:firebase_auth/firebase_auth.dart';

Future<String?> saveUserProfile({
    required String name,
    required String email,
}) async {
    final user = FirebaseAuth.instance.currentUser;

    if (user == null) {
        return 'Vous devez être connecté.';
    }

    if (name.trim().isEmpty) {
        return 'Le nom est obligatoire.';
    }

    try {
        await FirebaseFirestore.instance
                .collection('users')
                .doc(user.uid)
                .set({
                    'name': name.trim(),
                    'email': email.trim(),
                    'updatedAt': FieldValue.serverTimestamp(),
                }, SetOptions(merge: true));

        return null;
    } on FirebaseAuthException catch (e) {
        if (e.code == 'permission-denied') {
            return 'Vous n\'êtes pas autorisé à modifier ces données.';
        }

        if (e.code == 'unavailable') {
            return 'Le service est temporairement indisponible.';
        }

        return 'Impossible d\'enregistrer le profil.';
    } catch (_) {
        return 'Une erreur inattendue est survenue.';
    }
}

Cet exemple écrit dans le document correspondant à l'identifiant de l'utilisateur connecté. Cela ne suffit toutefois pas, à lui seul, à garantir la sécurité : les règles Firestore doivent imposer les autorisations appropriées et contrôler les données acceptées.

Sécuriser les données avec les règles Firestore :

Les règles Firestore s'exécutent indépendamment de la validation effectuée dans Fluter. Elles peuvent contrôler l'identité du demandeur, les droits d'accès et certaines propriétés des données.

Voici un exemple pédagogique pour une collection users où chaque utilisateur peut créer ou modifier son propre document.

rules_version = '2';

service cloud.firestore {
    match /databases/{database}/documents {

        match /users/{userId} {
            function isOwner() {
                return request.auth != null
                        && request.auth.uid == userId;
            }

            allow read: if isOwner();

            allow create: if isOwner()
                            && request.resource.data.keys().hasOnly([
                                'name',
                                'email',
                                'updatedAt'
                            ])
                            && request.resource.data.name is string
                            && request.resource.data.name.size() >= 2
                            && request.resource.data.name.size() <= 80
                            && request.resource.data.email is string;
            
            allow update: if isOwner()
                            && request.resource.data.keys().hasOnly([
                                'name',
                                'email',
                                'updatedAt'
                            ])
                            && request.resource.data.name is string
                            && request.resource.data.name.size() >= 2
                            && request.resource.data.name.size() <= 80
                            && request.resource.data.email is string;

            allow delete: if false;
        }
    }
}

Points importants :

  • request.auth != null vérifie qu'une identité authentifiée est disponible.

  • request.auth.uid == userId limite l'accès au document de l'utilisateur concerné.

  • keys().hasOnly(...) limite les champs présents aux noms autorisés.

  • Les vérifications de type et de longueur imposent des contraintes supplémentaires.

  • La suppression est interdite dans cet exemple.

Ces règles constituent un exemple de départ, pas une politique universelle. Elles autorisent ici la lecture du document entier par son propriétire et n'imposent pas que l'email corresponde à une adresse vérifiée dans Firebase Authentication.

Il faut aussi vérifier que les règles conviennet aux opérations réellement utilisées par l'application. Les accès effectués par les SDK serveur avec des prib-vilèges administratifs ne sont généralement pas contrôlés par les règles Firestore de la même manière que les accès des clients.

Ne pas laisser l'utilisateur modifier des champs sensibles :

Certains champs ne doivent pas être modifiables directement par un utilisateur ordinaire.

Par exemple :

  • role

  • isAdmin

  • isVerifiedByStaff

  • accountBalance

  • permissions

Une interface Flutter peut masquer ces champs, mais cela ne suffit pas : un client modifié pourrait tenter de les envoyer directement.

Les règles Firestore doivent empêcher les changements non autorisés. Pour les rôles privilégiés, utilisez un mécanisme de confiance, comme les custom claims attribués depuis un environnement serveur sécurisé, avec des règles adaptées.

Ne faites jamais confiance à une valeur envoyée par le client simplement parce qu'elle provient d'un formulaire Flutter.

Gérer les erreurs de Firebase Storage :

Lors de l'envoi d'une photo de profil ou d'un fichier, l'opération peut échouer pour plusieurs raisons :

  • Taille de fichier non autorisée.

  • Type de fichier non accepté.

  • Absence de permission.

  • Problème de réseau.

  • Erreur temporaire du service.

Exemple de gestion des erreurs :

import 'package:firebase_storage/firebase_storage.dart';

Future<String> uploadProfileImage(
    Reference storageRef,
    Strig filePath,
) aysnc {
    try {
        await storageRef.putFile(
            File(filePath),
            SettableMetadata(
                contentType: 'image/jpeg',
            ),
        );

        return null;
    } onFirebaseAuthException catch (e) {
        switch (e.code) {
            case 'unauthorized':
                return 'Vous n\'êtes pas autorisé à envoyer ce fichier.';
            case 'canceled':
                return 'L\'envoi du fichier a été annulé.';
            case 'retry-limit-exceeded':
                return 'L\'envoi a échoué après plusieurs tentatives.';
            default:
                return 'Impossible d\'envoyer la photo.';
        }
    } catch (_) {
        return 'Une erreur inattendue est survenue.';
    }
}

Pour compiler cet exemple, ajoutez également l'import dart:io si vous utilisez File.

Le champ contentType fourni par le client ne prouve pas que le fichier est réellement une image JPEG. Il faut compléter cette approche avec des règles Storage qui vérifient notamment l'identité, le chemin, le type déclaré et la taille autorisée. Pour les besoins plus stricts, une vérification côté serveur peut être nécessaire.

Afficher des messages d'erreur utiles :

Un message d'erreur doit aider l'utilisateur à comprendre quoi faire ensuite, sans exposer inutilement des informations internes.

Exemples :

Situation Message conseillé
Champ vide Ce champ est obligatoire.
Email mal formé Vérifiez le format de votre adresse email.
Connexion impossible Vérifiez votre connexion Internet et réessayez.
Accès refusé Vous n'êtes pas autorisé à effectuer cette action.

Évitez d'afficher directement à l'utilisateur des traces techniques, des détails internes ou des messages bruts qui ne lui permettent pas de résoudre le problème.

Pour le diagnostic, vous pouvez enregistrer les informations techniques utiles dans un système de journalisation adapté, sans y inclure de mots de passe, de jetons d'authentification ou d'autres secrets.

Éviter les erreurs fréquentes :

  • Erreur 1 : faire confiance uniquement au formulaire :

    Problème : les vérifications Flutter peuvent être contournées.

    Solution : appliquez des contrôles d'accès et de validation dans les règles Firebase et, lorsque nécessaire, côté serveur.

  • Erreur 2 : afficher toutes les exceptions directement :

    Problème : les messages techniques peuvent être incompréhensibles ou divulguer des détails inutiles.

    Solution : convertissez les erreurs connues en messages clairs et utilisez un message générique pour les erreurs inattendues.

  • Erreur 3 : ne pas gérer l'état de chargement :

    Problème : l'utilisateur peut envoyer plusieurs requêtes en appuyant plusieurs fois sur un bouton.

    Solution : désactivez temporairement le bouton pendant l'opération et rétablissez son état lorsque celle-ci est terminée.

  • Erreur 4 : confondre données validées et données fiables :

    Problème : une donnée conforme au format attendu peut quand même être fausse ou malveillante.

    Solution : vérifiez aussi les autorisations, les relations entre les données et les règles métier.

Tester les validations et les erreurs :

Avant de publier l'application, testez différents scénarios.

  • Un champ obligatoire est vide.

  • Une adresse email présente un format incorrect.

  • Un mot de passe ne respecte pas les exigences.

  • Deux mots de passe sont différents.

  • Un utilisateur non connecté tente d'accéder à une opération protégée.

  • Un utilisateur tente de modifier le document d'un autre utilisateur.

  • Une écriture FireStore contient un champ interdit.

  • Un fichier dépasse la taille maximale autorisée.

  • Le réseau devient indisponible pendant une requête.

  • Firebase refuse une opération.

Pour les règles Firestore et Storage, utilisez les outils de test disponibles, notamment les émulateurs Firebase, afin de vérifier les autorisations avant le déploiement.

Bonnes pratiques à retenir :

  1. Valider les formulaires avant d'envoyer les requêtes.

  2. Nettoyer les entrées textuelles lorsque c'est approprié, par exemple avec trim().

  3. Ne pas supposer qu'une adresse email valide au format existe réellement.

  4. Gérer les exceptions avec des blocs try/catch.

  5. Afficher des messages adaptés à l'utilisateur.

  6. Protéger les données avec des règles Firestore et Storage restrictives.

  7. Réserver les opérations sensibles à un environnement de confiance.

  8. Ne jamais enregistrer les mots de passe en clair.

  9. Tester les cas normaux, les erreurs et les tentatives d'accès non autorisées.

  10. Ne pas considérer la validation côté client comme une garantie de sécurité.

Conclusion :

La validation des données et la gestion des erreurs sont indispensables pour créer une application Flutter fiable connectée à Firebase.

Une application robuste combine trois éléments : une validation claire côté client, des règles de sécurité côté Firebase et une validation côté serveur pour les opérations métier sensibles.

Présentation du module :

Lorsqu'une application Flutter utilise Firebase Authentication, Cloud Firestore ou Firebase Storage, des erreurs peuvent survenir pendant l'inscription, la connexion, l'enregistrement des données ou l'envoi de fichiers.

    debugPrint('Fin du chargement du profil');
}

Pour une erreur, vous pouvez afficher un message explicite :

try {
    // Exécuter une opération.
} catch (error, stackTrace) {
    debugPrint('Échec de l\'opération :$error');
    debugPrintStack(stackTrace: stackTrace);
}

Le paramètre stackTrace permet d'obtenir la trace de l'exécution, qui indique notamment les appels ayant conduit à l'erreur.

Les journaux locaux ne constituent pas un système complet de suivi en production. Ils peuvent ne pas être accessibles lorsque le problème se produit sur l'appareil d'un utilisateur.

Évitez aussi d'enregistrer les mots de passe, les jetons d'accès, les codes de vérification ou les informations personnelles inutiles.

Installer Firebase Crashlytics :

Firebase Crashlytics est un service de suivi des plantages et des erreurs.

  1. Ajouter les dépendances :

    Dans le terminal, à la racine du projet Flutter, exécutez :

    flutter pub add firebase_core
    flutter pub add firebase_crashlytics

    Si le projet utilise déjà Firebase, firebase_core est peut-être déjà installé.

    Vérifiez également que le projet Flutter est correctement associé à votre projet Firebase.

  2. Initialiser Firebase et capturer les erreurs Flutter :

    Dans le fichier main.dart, vous pouvez configurer la capture des erreurs de cette manière :

    import 'dart:async';

import 'package:flutter/material.dart';
import 'package:firebase_core/firebase_core.dart';
import 'package:firebase_crashlytics/firebase_crashlytics.dart';

import 'firebase_options.dart';

Future<void> main() async {
    WidgetsFlutterBinding.ensureInitialized();

    await Firebase.initializeApp(
        options: DefaultFirebaseOptions.currentPlatform,
    );

    FlutterError.onError = FirebaseCrashlytics.instance.recordFlutterFatalError;

    PlatformDispatcher.instance.onError = (error, stack) {
        FirebaseCrashlytics.instance.recordError(
            error,
            stack,
            fatal: true,
        );

        return true;
    };

    runApp(const MyApp());
}

class MyApp extends StatelessWidget {
    const MyApp({super.key});

    @override
    Widget build(BuildContext context) {
        return const MaterialApp(
            home: Scaffold(
                body: Center(
                    child: Text('Application initialisée'),
                ),
            ),
        );
    }
}

    Cet exemple configure la capture des erreurs Flutter et des erreurs non gérées remontant au gestionnaire d'erreurs de la plateforme.

    Selon les types d'erreurs asynchrones et les plateformes ciblées, une configuration complémentaire peut être nécessaire. Consultez la documentation actuelle de Crashlytics pour adapter l'initialisation à votre projet.

  3. Comprendre les principaux éléments :

    • Firebase.initializeApp() initialise les services Firebase.

    • FlutterError.onError permet de traiter les erreurs signalées par le mécanisme d'erreurs Flutter.

    • PlatformDispatcher.instance.onError traite certaines erreurs non gérées au niveau de la plateforme.

    • recordFlutterFatalError() transmet une erreur Flutter considérée comme fatale.

    • recordError() permet d'enregistrer une erreur avec sa trace.

    Le booléen fatal doit refléter la gravité de l'erreur selon la manière dont votre application la traite. Une erreur récupérée correctement ne doit pas être automatiquement considérée comme fatale.

Enregistrer une erreur non fatale :

Certaines erreurs ne provoquent pas la fermeture de l'application, mais restent importantes pour le diagnostic.

Par exemple, une erreur lors du chargement d'un profil peut être enregistrée tout en permettant à l'utilisateur de continuer à utiliser l'application.

import 'package:firebase_crashlytics/firebase_crashlytics.dart';

        // Charger les données du profil depuis Firestore.
    } catch (error, stackTrace) {
        await FirebaseCrashlytics.instance.recordError(
            error,
            stackTrace,
            reason: 'Échec du chargement du profil',
            fatal: false,
        );
        
        // Afficher un message adapté dans l'interface.
    }
}

Il est important de ne pas masquer silencieusement les erreurs. Après leur enregistrement, l'application doit également appliquer une stratégie de récupération adaptée : afficher un message, réessayer si cela est pertinent ou revenir à un état sûr.

Ajouter des informations de diagnostic :

Une erreur est plus facile à comprendre lorsqu'elle est accompagnée d'informations contextuelles non sensibles.

Crashlytics permet d'ajouter des clés personnalisées :

await FirebaseCrashlytics.instance.setCustomKey(
    'screen',
    'profile',
);

await FirebaseCrashlytics.instance.setCustomKey(
    'operation',
    'load_profile',
);

Ces informations peuvent aider à déterminer l'écran et l'opération concernés.

Vous pouvez aussi définir un identifiant utilisateur pseudonyme pour faciliter le regroupement des raports :

);

Utilisez cette possibilité avec prudence : un identifiant stable reste une donnée potentiellement identifiable ou liée à une personne. Respectez les obligations de confidentialité et n'envoyez que les informations nécessaires au diagnostic.

Ne transmettez jamais de mot de passe, de jeton d'authentification, de code SMS ou de données bancaires comme informations de diagnostic.

Centraliser la gestion des erreurs Firebase :

Dans une application qui contient plusieurs écrans, il est préférable de ne pas réécrire la même logique de gestion des erreurs partout.

Vous pouvez créer un service chargé de convertir les exceptions en messages compréhensibles.

Exemple :

import 'package:firebase_auth/firebase_auth.dart';
import 'package:cloud_firestore/cloud_firestore.dart';

class AppErrorHandler {
    static String messageFor(Object error) {
        if (error is FirebaseAuthException) {
            switch (error.code) {
                case 'invalid-email':
                    return 'Le format de l\'adresse email est incorrect.';
                
                case 'network-request-failed':
                    return 'Vérifiez votre connexion Internet.';
                
                case 'weak-password':
                    return 'Le mot de passe ne respecte pas les exigences.';

                default:
                    return 'Une erreur d\'authentification est survenue.';
            }
        }

        if (error is FirebaseException) {
            switch (error.code) {
                case 'permission-denied':
                    return 'Vous n\'avez pas les autorisations nécessaires.';

                case 'unavailable':
                    return 'Le service est temporairement indisponible.';

                default:
                    return 'Une erreur Firebase est survenue.';
            }
        }

        return 'Une erreur inattendue est survenue.';
    }
}

Utilisation :

try {
    // Exécuter une opération Firebase.
} catch (error, stackTrace) {
    debugPrint('Erreur technique : $error');

    final message = AppErrorHandler.messageFor(error);

    // Afficher le message dans l'interface.
}

Dans cet exemple, la trace est affichée dans les journaux de développement. En production, évitez d'afficher directement les détails techniques à l'utilisateur.

La liste des codes doit être adaptée aux opérations réellement utilisées et à la version des bibliothèques Firebase.

Distinguer une erreur technique d'une erreur métier :

Toutes les erreurs ne nécessitent pas le même traitement.

Erreur technique :

Exemples :

  • Une requête échoue à cause du réseau.

  • Le service est indisponible.

  • Une exception inattendue survient.

Actions possibles :

  • Enregistrer l'erreur.

  • Afficher un message générique.

  • Proposer une nouvelle tentative si elle est sûre.

Erreur métier :

Exemples :

  • Un champ obligatoire est manquant.

  • Un utilisateur ne peut pas effectuer une action selon son rôle.

  • Une opération ne respecte pas une règle fonctionnelle.

Actions possibles :

  • Expliquer la règle à l'utilisateur.

  • Corriger les données saisies.

  • Vérifier les autorisations côté Firebase ou côté serveur.

Il ne faut pas enregistrer chaque validation de formulaire échouée comme un plantage. Les rapports doivent rester utiles et exploitables.

Tester Crashlytics :

Avant de dépendre de Crashlytics en production, vérifiez que les rapportssont effectivement transmis et visibles dans la console Firebase.

Pour tester une erreur non fatale :

    StackTrace.current,

Les rapports peuvent ne pas apparaître immédiatement. Vérifiez également la configuration Firebase, la plateforme ciblée et les paramètres de compilation si aucun rapport n'est reçu.

  1. Configurez Crashlytics pour les plateformes prises en charge.

  6. Évitez les doublons inutiles lors de la capture d'une même exception.

  7. Ne transmettez pas de secrets ni de données personnelles inutiles.

Présentation du module :

Pourquoi automatiser les tests ?

Sans tests automatisés, il faut souvent relancer l'application, remplir les formulaires, se connecter, modifier le profil, vérifier les données et reproduire manuellement les différents scénarios.

Cette méthode présente plusieurs limites :

  • elle prend du temps;

  • certaines erreurs passent inaperçues;

  • les mêmes vérifications doivent être répétées;

  • les régressions peuvent apparaître après une modification;

  • les tests manuels ne couvrent pas toujours les cas inhabituels.

Un test automatisé exécute une série de vérifications et indique si le résultat obtenu correspond au résultat attendu.

Par exemple, une fonction de validation d'adresse email doit accepter une adresse valide et refuser une chaîne vide. Un test peut vérifier ces deux comportements automatiquement.

Les tests ne garatissent pas l'absence totale de bugs. Ils permettent cependant de détecter plus tôt de nombreuses erreurs et de réduire les risques lors des évolutions de l'application.

Comprendre les différents types de tests :

  1. Les tests unitaires :

    Les tests unitaires vérifient le comportement d'une petite partie du code, généralement une fonction, une méthode ou une classe.

    Ils sont particulièrement adaptés aux éléments suivants :

    • validation des adresses email;

    • vérification des mots de passe;

    • convesion et formatage des données;

    • calculs;

    • règles métier;

    • fonctions de transformation des données;

    • gestion de certaines erreurs.

    Un test unitaire doit être aussi indépendant que possible des services externes.

    Par exemple, une fonction qui vérifie le format d'une adresse email n'a pas besoin de se connecter à Firebase.

  2. Les tests de widgets :

    Les tests de widgets vérifient le comportement d'une interface Flutter.

    Ils peuvent contrôler :

    • la présence d'un titre;

    • l'affichage d'un champ de saisie;

    • la présence d'un bouton;

    • l'affichage d'un message d'erreur;

    • la réaction à un clic;

    • le comportement d'un formulaire;

    • la mise à jour de l'interface après une action.

    Ces tests utilisent notamment le WidgetTester, qui permet de construire des widgets, de simuler des interactions et de rechercher des éléments dans l'arbre des widgets.

  3. Les tests d'intégration :

    Les tests d'intégration vérifient que plusieurs composants fonctionnent correctement ensemble.

    Ils peuvent notamment couvrir :

    • le parcours d'inscription;

    • la connexion d'un utilisateur;

    • la récupération du profil dans Firestore;

    • la modification des informations du compte;

    • l'envoi d'un fichier vers Firebase Storage;

    • la déconnexion;

    • la navigaion entre plusieurs écrans.

    Les tests d'intégration sont plus proches des conditions réelles d'utilisation. Ils peuvent nécessiter un émulateur, un appareil ou un similateur, et leur exécution est généralement plus longue.

  4. Les tests des règles de sécurité Firebase :

    Les tests des règles de sécurité vérifient si les accès aux données sont autorisés ou refusés conformément aux règles configurées dans Firebase.

    Par exemple, pour une collection users, on peut vouloir que :

    • un utilisateur connecté puisse lire son propre profil;

    • un utilisateur ne puisse pas lire le profil d'un autre utilisateur;

    • un utilisateur ne puisse pas modifier les rôles privilégiés de son compte;

    • un utilisateur non connecté ne puisse pas accéder aux profils privés.

    Ces tests sont essentiels, car masquer un bouton dans l'interface ne constitue pas une protection suffisante. Les autorisations doivent être imposées par les règles du service Firebase concerné.

Écrire un premier test unitaire :

Pour commencer, nous allons créer une fonction de validation d'adresse email.

  1. Créer la fonction de validation :

    Créez le fichier lib/validator/email_validator.dart :

    class EmailValidator {
    static bool isValid(String email) {
        final normalizedEmail = email.trim();

        final emailRegex = RegExp(
            r'^[^@\s]+@[^@\s]+\.[^@\s]+$',
        );

        return emailRegex.hasMatch(normalizedEmail);
    }
}

    Cette fonction supprime les espaces situés au début et à la fin de la chaîne, puis vérifie une structure générale d'adresse email.

    Cette expression régulière constitue une validation élémentaire. Elle ne garantit pas que l'adresse existe, qu'elle reçoit des messages ou qu'elle respecte toutes les règles possibles d'une adresse email.

    La vérification de l'adresse lors de l'inscription doit donc être complétée par le mécanisme de vérification d'email de Firebase Authentication lorsque celui-ci est utilisé.

  2. Écrire les tests unitaires :

            expect(

            );
        });

Lestests ne doivent pas seuelement vérifier les scénarios habituels. Ils doivent également couvrir les entrées inattendues.

Pour une validation d'adresse email, les cas suivants peuvent être étudiés :

  • chaîne vide;

  • espaces seuls;

  • adresse sans arobase;

  • adresse sans domaine;

  • plusieurs caractères @;

  • espaces à l'intérieur de l'adresse;

  • caractères inhabituels;

  • adresse valide entourée d'espaces.

On peut compléter le test précédent avec une liste de valeurs invalides :

test('refuse plusieurs formats invalides', () {
    const invalidEmails = [
        '',
        '    ',
        'utilisateur',
        'utilisateur@',
        '@example.com',
        'utilisateur example@example.com',
    ];

    for (final email in invalidEmails) {
        except(
            EmailValidator.isValid(email),
            isFalse,
            reason: 'Adresse inattendue : $email',
        );
    }
});

Cette approche permet de vérifier plusieurs entrées avec un même scénario. Pour des comportements plus complexes, il peut être préférable de créer un test distinct par cas afin de faciliter le diagnostic.

Tester un widget Flutter :

Nous allons maintenant tester un formulaire de connexion simplifié.

  1. Créer un widget de formulaire :

    Créez le fichier lib/widgets/login_form.dart :

    import 'package:flutter/material.dart';

class LoginForm extends StatefulWidget {
    const LoginForm({
        super.key,
        required this.onSubmit,
    });

    final void Function(String email, String password) onSubmit;

    @override
    State<LoginForm> createState() => _LoginFormState();
}

class _LoginFormState extends State<LoginForm> {
    final _formKey = GlobalKey<FormState>();
    final _emailController = TextEditingController();
    final _passwordController = TextEditingController();

    @override
    void dispose() {
        _emailController.dispose();
        _passwordController.dispose();
        super.dispose();
    }

    void _submit() {
        if (!_formKey.currentState!.validate()) {
            return;
        }

        widget.onSubmit(
            _emailController.text.trim(),
            _passwordController.text,
        );
    }

    @override
    Widget build(BuildContext context) {
        return Form(
            key: _formKey,
            child: Column(
                mainAxisSize: MainAxisSize.min,
                children: [
                    TextFormField(
                        key: const Key('emailField'),
                        controller: _emailController,
                        decoration: const InputDecoration(
                            labelText: 'Adresse email',
                        ),
                        keyboardType: TextInputType.emailAddress,
                        validator: (value) {
                            final email = value?.trim() ?? '';

                            if (email.isEmpty) {
                                return 'Veuillez saisir une adresse email';
                            }

                            if (!email.contains('@')) {
                                return 'Adresse email invalide',
                            }

                            return null;
                        },
                    ),
                    TextFormField(
                        key: const Key('passwordField'),
                        controller: _passwordController,
                        decoration: const InputDecoration(
                            labelText: 'Mot de passe',
                        ),
                        obscureText: true,
                        validator: (value) {
                            if (value == null || value.isEmpty) {
                                return 'Veuillez saisir un mot de passe';
                            }

                            return null;
                        },
                    ),
                    const SizedBox(height: 16),
                    ElevatedButton(
                        key: const Key('loginButton'),
                        onPressed: _submit,
                        child: const Text('Se connecter'),
                    ),
                ],
            ),
        );
    }
}

    Ce widget valide les champs et appelle onSubmit uniquement si les deux champs passent leurs validations.

    Il ne se connecte pas directement à Firebase. Cette séparation facilité les tests, car nous pouvons vérifier le comportement du formulaire sans effectuer de véritable connexion.

    Dans une application complète, la fonction onSubmit pourra être reliée à un service d'authentification.

Préparer les tests Firebase :

Les tests qui utilisent Firebase doivent être organisés avec soin. Une erreur de configuration peut entraîner des connexions à un projet réel ou modifier des données qui ne sont pas destinées aux tests.

Il est donc préférable de séparer les environnements suivants :

  • Développement : pour le travail quotidien.

  • Test : pour les vérifications automatisées.

  • Production : pour les utilisateurs réels.

Lorsque c'est possible, les tests automatisés qui nécessitent un service Firebase doivent utiliser les émulateurs Firebase.

  1. Installer ou vérifier la Firebase CLI :

    La Firebase CLI permet de configurer et de lancer la suite d'émulateurs.

    Vérifiez si elle est disponible :

    firebase --version

    Si la commande n'est pas disponible, installez la Firebase CLI selon les instructions officielles de Firebase.

    Vous devez également disposer de Node.js et de nom pour les outils de test JavaScript utilisés dans les sections consacrées aux règles de sécurité.

  2. Initialiser les émulateurs :

    À la racine du projet Firebase, exécutez :

    firebase init emulators

    Sélectionnez les services nécessaires au projet, par exemple :

    • Authentication;

    • Cloud Firestore;

    • éventuellement Storage.

    Les choix disponibles peuvent dépendre de la version de la Firebase CLI. Vérifiez les ports et les paramètres générés dans firebase.json.

    Une configuration possible ressemble à ceci :

    {
    "emulators": {
        "auth": {
            "port": 9099
        },
        "firestore": {
            "port": 8080
        },
        "storage": {
            "port": 9199
        },
        "ui": {
            "enabled": true,
            "port": 4000
        }
    }
}

    Cette configuration est un exemple. Si le fichier firebase.json existe déjà, conservez les autres paramètres nécessaires au projet et fusionnez uniquement les sections appropriées.

  3. Lancer les émulateurs :

    Pour démarrer les services configurés :

    firebase emulators:start

    Les ports de l'exemple correspondent à ceux souvent utilisés par les émulateurs Authentication, Firestore et Storage.

    La sortie du terminal indique les services réellement démarrés et leurs adresses locales.

    Pour arrêter les émulateurs, interrompez le processus dans le terminal.

    L'utilisation des émulateurs permet de tester les interactions sans dépendre systématiquement des services de production. Toutefois, chaque émulateur doit être configuré correctement, et les tests doivent vérifier qu'ils se connectent bien à l'environnement local attendu.

Connecter Flutter aux émulateurs Firebase :

Dans une application FLutter, les services Firebase sont généralement initialisésau démarrage.

Par exemple :

await Firebase.initializeApp(
    options: DefaultFirebaseOptions.currentPlatform,
);

Cette initialisation est habituellement générée ou configurée avec FlutterFire CLI.

Pour les tests, il faut ensuite rediriger les services concernés vers les émulateurs avant de les utiliser.

  1. Exemple avec Firebase Authentication :

    Après l'initialisation de Firebase, une configuration de test peut utiliser :

    await FirebaseAuth.instance.useAuthEmulator(
    '10.0.2.2',
    9099,
);

    L'adresse 10.0.2.2 est couramment utilisée par un émulateur Android pour joindre la machine hôte.

    Sur un simulateur iOS ou un navigateur exécuté sur la même machine, l'adresse différente. Sur un appareil physique, il faut généralement utiliser l'adresse IP de l'ordinateur, avec une configuration réseau adaptée.

    Ne considérez donc pas 10.0.2.2 comme une adresse universelle.

  2. Exemple avec Cloud Firestore :

    Pour Cloud Firestore, on peut configurer l'émulateur de cette manière :

    FirebaseFirestore.instance.useFirestoreEmulator(
    '10.0.2.2',
    8080,
);

  3. Exemple avec Firebase Storage :

    Pour Storage, on peut utiliser :

    await FirebaseStorage.instance.useStorageEmulator(
    '10.0.2.2',
    9199,
);

    Vérfiez la signature exacte des méthodes avec la version des paquets Firebase installée dans le projet.

  4. Attention à l'initialisation :

    Ces méthodes doivent être appelées avant les premières opérations sur les services concernés. Il est préférable de centraliser cette configuration dans un point d'entrée spécifique aux tests.

    Par exemple, on peut créer une fonction d'initialisation qui :

    1. initialise Firebase;

    2. configure Authentication sur son émulateur;

    3. configure Firestore sur son émulateur;

    4. configure Storage si nécessaire;

    5. lance ensuite le scénario de test.

    Il faut aussi éviter de connecter accidentellement les tests à la production. Les environnements doivent être explicitement sélectionnés, et les tests destructifs ne doivent pas être exécutés sur les données réelles.

Tester les parcours d'authentification :

Les modules précédents ont introduit l'inscription, la connexion, la vérification de l'adresse email, l'authentification par SMS, la gestion des sessions et la réinitialisation du mot de passe.

Chaque parcours peut être décomposé en scénarios vérifiables.

  1. Scénarios d'inscription :

    Les tests peuvent vérifier que :

    • un formulaire valide transmet les données attendues;

    • une adresse email vide est refusée;

    • un mot de passe manquant est refusé;

    • une erreur d'inscription est correctement présentée à l'utilisateur;

    • l'interface affiche l'état de chargment lorsque l'opération est en cours;

    • une inscription réussie mène à l'écran prévu.

    Un test de widget peut vérfier les validations sans contacter Firebase. Un test d'intégration peut ensuite vérifier le parcours complet avec l'émulateur Authentication.

  2. Scénarios de connexion :

    Il est utile de tester les situations suivantes :

    • identifiants valides;

    • adresse email incorrecte;

    • mot de passe incorrect;

    • utilisateur inexistant;

    • erreur réseau simulée ou indisponibilité du service;

    • opération de connexion déjà en cours;

    • déconnexion après une connexion réussie.

    Le but n'est pas uniquement de vérifier que la connexion fonctionne. Il faut aussi s'assurer que l'application réagit correctement aux échecs.

  3. Scénarios de session :

    Pour la gestion des sessions, vérifiez notamment :

    • qu'un utilisateur connecté accède aux écrans protégés;

    • qu'un utilisateur déconnecté ne peut pas accéder aux données privées;

    • que l'état de l'interface suit les changements d'authentification;

    • que la déconnexion redirige vers l'écran attendu;

    • que les données d'un utilisateur ne restent pas visibles après le changement de compte.

    Ces scénarios doivent être vérifiés à la fois dans l'interface et au niveau des autorisations côté Firebase.

  4. Scénarios de vérification d'email et de SMS :

    Pour la vérification de l'adresse email, testez l'état de l'interface avant et après la confirmation de la vérification, ainsi que la gestion des erreurs de renvoi.

    Pour l'authentification par téléphone, testez les étapes d'envoi du code, de validation du code et de gestion des erreurs.

    Les flux SMS et les mécanismes de vérification peuvent avoir des contraintes spécifiques selon l'environnement. Pour automatiser ces parcours, utilisez les possibilités prévues par Firebase, notamment les numéros de téléphone de test lorsque c'est approprié, et évitez de dépendre d'un véritable SMS pour chaque exécution.

Écrire un test d'intégration Flutter :

Un test d'intégration démarre l'application et effectue des interactions plus proches de celles d'un utilisateur.

Créez le fichier integration_test/authentication_test.dart :

                findsOneWidget,
            );
        },

}

Remplacez mon_application par le nom du package utilisé par le projet.

Ce test suppose que l'application démarre sur un écran contenant le texte "Se connecter". Si l'application affiche un écran d'accueil, un écran de chargement ou une redirection automatique, adaptez le test au comportement réel de votre application.

  1. Exécuter le test d'intégration :

    Lancez un élmulateur Android, un simulateur iOS ou connectez un appareil compatible.

    Puis exécutez :

    flutter test integration_test/authentication_test.dart

    La disponibilité de la cible et les prérequis d'exécution dépendent de la plateforme utilisée.

  2. Tester un parcours complet :

    Une fois le test de démarrage fonctionnel, vous pouvez ajouter des interactions pour :

    1. saisir une adresse email;

    2. saisir un mot de passe de test;

    3. appuyer sur le bouton de connexion;

    4. attendre la réponse de l'application;

    5. vérifier l'écran affiché après la connexion;

    6. vérifier le profil chargé;

    7. se déconnecter;

    8. vérifier le retour à l'écran non authentifié.

    Pour tester une véritable connexion, le service d'authentification doit être configuré sur l'émulateur et un compte de test doit être préparé.

    Le test ne doit pas supposer que Firebase a répondu instantanément. Les opérations asynchrones doivent être attendues, et les conditions de réussite doivent être explicites.

Tester les règles de sécurité de Cloud Firestore :

Les tests de sécurité sont différents des tests de widgets. Ils vérifient si Firebase autorise ou refuse les opérations sur les données.

Dans cette section, nous utiliserons le SDK de tst des règles Firebase en JavaScript. Ces tests sont exécutés dans un environnement Node.js et non directement par flutter test.

  1. Exemple de règles Firestore :

    Supposons que chaque utilisateur possède un document dans la collection users, dont l'identifiant correspond à son UID Firebase.

    Un exemple de règles pourrait être :

    rules_version = '2';

service cloud.firestore {
    match /databases/{database}/documents {
        match /users/{userId} {
            allow read: if request.auth != null
                        && request.auth.uid == userId;

            allow create: if request.auth != null
                            && request.auth.uid == userId
                            && !request.resource.data.keys()
                                        .hasAny(['role']);

            allow update: if request.auth != null
                            && request.auth.uid == userId
                            && request.resource.data.role
                                        == resource.data.role;
            
            allow delete: if request.auth != null
                            && request.auth.uid == userId;
        }
    }
}

    Cet exemple illustre plusieurs principes :

    • un utilisateur doit être authentifié pour accéder à son document;

    • son UID doit correspondre à l'identifiant du document;

    • la création d'un profil ne peut pas fournir le champ role;

    • la modificationdu profil ne peut pas changer le rôle existant.

    Cet exemple doit être adapté à votre modèle de données. En particulier,l'accès à request.resource.data.role lors d'une mise à jour suppose que le document contient ce champ. Si ce champ est absent, la règle peut refuser l'opération. Les règlesci-dessus ne constituent pas une solution universelle pour tous les modèles de profils.

    Si votre application utilise un autre mécanisme de gestion des rôles, il faut définir les autorisations à partir de la source de confiance choisie. Il ne faut jamais faire confiance à une valeur de rôle fournie librement par le client.

  2. Installer les outils de test des règles :

    Dans un dossierde tests Firebase séparé, initialisez un projet Node.js :

    npm init -y

    Installez les dépendances de test :

    nom install --save-dev @firebase/rules-unit-testing firebase vitest

    Les tests ci-dessous utilisent Vitest et le SDK @firebase/rules-unit-testing.

    Ajoutez un script dans le fichier package.json :

    {
    "scripts": {
        "test": "vitest run"
    }
}

    Si votre fichier package.json contient déjà d'autres scripts ou paramètres, conservez-les et ajoutez uniquement le script nécessaire.

  3. Créer les tests de règles :

    Créez un fichier firestore.rules.test.js dans le dossier de tests Firebase :

    import { readFile } from 'node:fs/promises';
import {
    afterAll,
    beforeAll,
    beforeEach,
    describe,
    it,
} from 'vitest';

import {
    initializeTestEnvironment,
    assertSucceeds,
    assertFails,
} from '@firebase/rules-unit-testing';

import {
    doc,
    getDoc,
    setDoc,
    updateDoc,
} from 'firebase/firestore';

let testEnv;

beforeAll(async () => {
    const rules = await readFile(
        '../firestore.rules',
        'utf8',
    );

    testEnv = await initializeTestEnvironment({
        projectId: 'demo-flutter-firebase-tests',
        firestore: {
            rules,
        },
    });
});

beforeEach(async () => {
    await testEnv.clearFirestore();
});

afterAll(async () => {
    await testEnv.cleanup();
});

describe('Règles de sécurité des profils', () => {
    it('autorise un utilisateur à lire son profil', async () => {
        await testEnv.withSecurityRulesDisabled(
            async (context) => {
                await setDoc(
                    doc(context.firestore(), 'users/user-1'),
                    {
                        displayName: 'Utilisateur de test',
                        role: 'user',
                    },
                );
            },
        );

        const db = testEnv
                    .authenticatedContext('user-1')
                    .firestore();
        
        await assertSucceeds(
            getDoc(doc(db, 'users/user-1')),
        );
    });

    it('refuse la lecture du profil d\'un autre utilisateur', async () => {
        await testEnv.withSecurityRulesDisabled(
            async (context) => {
                await setDoc(
                    doc(context.firestore(), 'users/user-2'),
                    {
                        displayName: 'Autre utilisateur',
                        role: 'user',
                    },
                );
            },
        );

        const db = testEnv
                    .authenticatedContext('user-1')
                    .firestore();
        
        await assertFails(
            getDoc(doc(db, 'users/user-2')),
        );
    });

    it('refuse la création d\'un profil avec un rôle fourni par le client', async () => {
        const db = testEnv
                    .authenticatedContext('user-1')
                    .firestore();

        await assertFails(
            setDoc(
                doc(db, 'users/user-1'),
                {
                    displayName: 'Utilisateur de test',
                    role: 'admin',
                },
            ),
        );
    });

    it('refuse la modification du rôle existant', async () => {
        await testEnv.withSecurityRulesDisabled(
            async (context) => {
                await setDoc(
                    doc(context.firestore(), 'users/user-1'),
                    {
                        displayName: 'Utilisateur de test',
                        role: 'user',
                    },
                );
            },
        );

        const db = testEnv
                    .authenticatedContext('user-1')
                    .firestore();
        
        await assertFails(
            updateDoc(
                doc(db, 'users/user-1'),
                {
                    role: 'admin',
                },
            ),
        );
    });

    it('refuse l\'accès à un utilisateur non connecté', async () => {
        await testEnv.withSecurityRulesDisabled(
            async (context) => {
                await setDoc(
                    doc(context.firestore(), 'users/user-1'),
                    {
                        displayName: 'Utilisateur de test',
                        role: 'user',
                    },
                );
            },
        );

        const db = testEnv.unauthenticatedContext().firestore();

        await assertFails(
            getDoc(doc(db, 'users/user-1')),
        );
    });
});

    Adaptez le chemin ../firestore.rules à l'emplacement réel du fichier de règles. Le chemon est résolu relativement au répertoire depuis lequel le processus de test s'exécute; vérifiez qu'il correspond bien à l'organisatiion de votre projet.

    Dans ces tests, withSecurityRulesDisabled() sert uniquement à préparer les données de départ sans appliquer les règles. Les opérations testées ensuite passent par les règles de sécurité.

    Le projet utilisé ici porte un identifiant de démonstration. Pour des tests locaux, configurez correcteemnt l'émulateur Firestore et assurez-vous que les données restent isolées de la production.

  4. Exécuter les tests de règles :

    Lancez d'abord l'émulateur Firestore :

    firebase emulators:start --only firestore

    Dans un autre terminal, exécutez les tests avec la commande prévue dans le projet Node.js :

    npm test

    Si Vitest n'arrive pas à joindre l'émulateur, vérifiez que celui-ci est démarré, que le projet de test utilise le bon identifiant et que la configuration des émulateurs est cohérente.

    La commande npm test exécute les tests JavaScript; elle ne remplace pas flutter test.

  5. Comprendre les résultats :

    Dans les tests de règles :

    • assertSucceeds() vérifie qu'une opération est autorisée;

    • assertFails() vérifie qu'une opération est refusée.

    Un test de sécurité ne doit pas seulement démontrer que les utilisateurs légitimes peuvent accéder aux données. Il doit aussi démontrer que les accès interdits sont effectivement refusés.

    Il est utile de tester les accès d'un utilisateur à son propre document, aux documents d'autres utilisateurs, aux documents inexistants et aux opérations non autorisées sur les champs sensibles.

Tester les règles de sécurité de Firebase Storage :

Si l'application permet de stocker des photos de profil ou d'autres fichiers, il faut aussi vérifier les règles de Storage.

Par exemple, les règles peuvent exiger que l'utilisateur soit authentifié et que le fichier soit placé dans un espace qui lui appartient.

Un schéma de règle illustratif peut être :

rules_version = '2';

service firebase.storage {
    match /b/{bucket}/o {
        match /users/{userId}/{fileName} {
            allow read, write: if request.auth != null
                                && request.auth.uid == userId;
        }
    }
}

Ce modèle limite l'accès au chemin associé à l'UID. Dans une application réele, il peut être nécessaire d'ajouter des restrictions sur la taille des fichiers, leur type de contenu, les opérations autorisées et les exigences de confidentialité.

Les tests de Storage doivent vérifier les accès autorisés et refusés, comme pour Firestore. Ils doivent être réalisés sur l'émulateur Storage lorsqu'il est configuré pour les tests.

N'oubliez pas que les règles Firestore et les règles Storage sont deux mécanismes distincts. Protéger les documents de profil ne protège pas automatiquement les fichiers associés.

Tester les erreurs et les opérations asynchrones :

Les applications Flutter utilisant Firebase reposent fréquemment sur des opératins asynchrones.

Par exemple :

try {
    await FirebaseAuth.instance.signInWithEmailAndPassword(
        email: email,
        password: password,
    );
} on FirebaseAuthException catch (error) {
    // Convertir l'erreur en message adapté à l'utilisateur.
}

Il est important de vérifier non seulement la réussite de l'opération, mais aussi le comportement de l'application en cas d'échec.

Les tests peuvent couvrir :

  • identifiants incorrects;

  • absence de connexion au service;

  • opération interrompue;

  • document Firestore inexistant;

  • refus d'accès par les règles de sécurité;

  • fichiers trop volumineux;

  • erreur de téléchargement;

  • expiration ou invalidité d'un code de vérification.

Les erreurs techniques ne doivent pas nécessairement être affichées telles quelles à l'utilisateur. Le code peut les convertir en messages compréhensibles, tout en conservant suffisamment d'informations pour le diagnostic.

Les tests doivent vérifier que l'application affiche le bon état après une erreur, par exemple en arrêtant l'indicateur de chargement l'indicateur de chargement et en permettant une nouvelle tentative.

Éviter les tests fragiles :

Un test fragile échoue pour une raison qui ne correspond pas à un véritable défaut fonctionnel, ou dépend excessivement de détails susceptibles de changer.

Pour rendre les tests plus fiables :

  1. Donnez un nom explicite à chaque scénario.

  2. Vérifiez un comportement précis.

  3. Utilisez des données de test déterministes.

  4. Évitez les dépendances aux services de production.

  5. Attendez les opérations asynchrones.

  6. Ne dépendez pas de délaisarbitraires lorsque des conditions observables peuvent être utilisées.

  7. Isolez les données entre les tests.

  8. Nettoyez les ressources créées par les scénarios.

  9. Ne stockez pas de secrets dans le code de test.

  10. Vérifiez aussi les cas d'échec.

Il est également important d'éviter que l'ordre d'exécution des tests modifie leurs résultats. Chaque scénario doit préparer ses propres données et ne pas dépendre d'un test exécuté précédemment.

Organiser une stratégie de tests :

Il n'est pas nécessaire de tester immédiatement chaque ligne de code. Il faut commencer par les fonctionnalités les plus importantes et construire une couverture progressive.

Une stratégie adaptée à notre application pourrait être :

Niveau Éléments à tester Exemple
Tests unitaires Fonctions indépendantes Validation d'email
Tests de widgets Interfaces et interactions Formulaire de connexion
Tests de services Logique liée à Firebase Gestion des erreurs d'authentification
Tests de services Logique liée à Firebase Gestion des erreurs d'authentification
Tests d'intégration Parcours complets Connexion puis déconnexion
Tests des règles Firestore Autorisation des documents Lecture du profil personnel
Tests des règles Storage Accès aux fichiers Téléversement dans le dossier personnel

Les tests unitaires sont généralement les plus rapides et les plus simples à exécuter. Les tests d'intégration et les tests des règles demandent une configuration supplémentaire, mais ils couvrent des risques différents.

Une bonne stratégie combine ces niveaux au lieu de dépendre d'un seul type de test.

flutter pub get
